# Semgrep 정적 보안 스캔 도입 (2026-10-27)

수작업 보안 감사(run-001~004, P0/P1 0건)를 Semgrep으로 CI화한 기록.
조사 근거: `docs/github-test-ai-research-20261027.md` 1-4절 (Semgrep ★17,293·LGPL-2.1 —
스캐너로 쓰는 것이지 코드를 복사하는 것이 아니라 라이선스 문제 없음).

## 설치

- 방법: Python 가상환경에 pip 설치 (시스템 Python 오염 없음, 프로덕션 의존성 추가 없음)
  ```sh
  python3 -m venv ~/.venvs/myhub-semgrep
  ~/.venvs/myhub-semgrep/bin/pip install semgrep
  ```
- 버전: semgrep 1.182.1 (2026-10-27 설치 시점)
- 가상환경 위치 `~/.venvs/myhub-semgrep`은 저장소 밖이라 `.gitignore` 변경 불필요.
  `SEMGREP_BIN` 환경변수로 다른 경로의 semgrep 바이너리를 지정할 수 있다.

## 사용법

```sh
npm run lint:security            # 전체 스캔 (텍스트 출력)
bash scripts/run-semgrep.sh --json   # JSON 출력 (기록용)
bash scripts/run-semgrep.sh --sarif  # SARIF 출력
```

실행 스크립트: `scripts/run-semgrep.sh` — 공식 규칙셋 + 커스텀 규칙을 함께 실행한다.
제외 범위: `backups/`(사용자 데이터 수출물, 코드 아님), `coverage/`, `dist/`,
`.wrangler/`, `node_modules/`.

정제 과정에서 발견한 semgrep 동작 특성(재현 프로브로 확인):
- `metavariable-regex`는 전일치(full-match) 의미라 양쪽에 `.*`가 필요하다.
  `API_KEY$` 같은 앵커는 동작하지 않는다.
- 백틱 템플릿 리터럴 안의 `...` 엘리시스는 매칭되지 않는다.
  (`myhub-locked-memo-query-without-filter`는 `$SQL` 메타변수 + 정규식 방식으로 변경)
- 규칙 `paths`의 include/exclude는 루트 앵커(`/src/...`) 형태로 써야
  deprecation 경고를 피할 수 있다.

### 스캔 커버리지 한계 (정직한 기록 — finding 0건이 "없음"의 증거는 아니다)

1. **public/*.html 인라인 스크립트는 Semgrep JS 규칙이 분석하지 않는다.**
   `innerHTML` 사용처(public/agent.html 등)는 `esc()` 이스케이프 패턴을 쓰고 있으나
   정적 커버리지는 없다. 프론트 XSS는 기존 수작업 감사로 보완해야 한다.
2. **public/js/memo-bundle.js:693 부분 파싱 오류.** semgrep이 정규식 내 `/`를
   파싱하지 못해 해당 파일 일부를 스킵했다. `node --check` 통과로 코드 자체는
   유효함을 확인했다. 번들은 생성물이라 스캔에서 제외하고 원본
   `public/js/memo/*.js`를 스캔한다.
3. **taint 기반 XSS/SQLi 규칙이 0건을 낸 것은 탐지 범위 내 0건이라는 의미다.**
   D1 `prepare()`의 문자열 조립 패턴은 공식 taint 규칙이 잡지 못해 커스텀 규칙으로
   보완했다 (위 22건 전수 확인).

### 환경 메모 (워크트리 node_modules 손상 — 이번 작업과 무관한 기존 문제)

- 복구: 메인 저장소 node_modules에서 하드링크로 11,163개 파일을 복원하고,
  없는 266개 파일은 `git show`로 복원했다 (최종 수정 파일 0건으로 확인).
  **주의: 복원된 파일 중 하드링크된 것은 메인 저장소와 inode를 공유한다.
  이 워크트리에서 node_modules 파일을 직접 수정하면 메인 저장소에도 반영되니
  수정하지 말 것.**
- VM 쓰기 장애: 작업 중반부터 간헐적으로 모든 프로세스의 `write()`가
  `EPERM`으로 실패하거나 조용히 0바이트가 되는 현상이 발생했다
  (strace 확인: `write(fd, ..., N) = -1 EPERM`). 수십 초~수 분 대기하면
  복구되는 패턴. 이 때문에 `npm install`, `git checkout`, `git status`
  (index.lock 쓰기)가 반복 실패했고, `git --no-optional-locks status`와
  재시도 루프로 우회했다. 장애 원인은 VM/스토리지 층으로 보이며 이 작업
  범위를 벗어난다. (참고: `muse.write`/`muse.edit` 파일 도구는 정상 동작했다.)
- `git status`는 `--no-optional-locks` 없이는 index.lock 쓰기 실패로
  동작하지 않을 때가 있다. 커밋 시에도 같은 문제가 생기면 대기 후 재시도할 것.
