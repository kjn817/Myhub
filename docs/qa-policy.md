# MyHub QA 정책

**제정**: 2026-10-12 (GPT 12/13/14/15차)
**적용**: 모든 개발 턴에 공통 적용

## 1. QA 필수 절차

모든 코드 수정 또는 기능 추가 시 다음 절차를 완료해야 함.

### Step 1. 자동 검증
- [ ] TypeScript 검사 (`npx tsc --noEmit`)
- [ ] 실제 배포용 빌드 (esbuild)
- [ ] Jest 전체 회귀 테스트
- [ ] 신규 기능 테스트
- [ ] DB 스키마 호환성 확인
- [ ] 기존 보안 정책 유지 확인

### Step 2. 브라우저 QA
스테이징에서 실제 사용자 시나리오를 수행. 페이지 200 확인만으로는 불충분.

**원칙**: 짧고 독립적인 시나리오로 분리하여 실행. 긴 세션은 중단 위험 있음.

### Step 3. 오류 수정 및 재검증
QA 중 발견된 문제는 현재 턴에서 수정하고 재검증.
"추후 수정 예정"으로 보고하지 않음.

## 2. QA 단계별 범위

### 매 턴 Smoke QA (필수)
- 로그인 상태 확인
- 주요 페이지 접근 (`/`, `/memo.html`, `/chat.html`)
- 메모·일정·할 일 목록 조회
- AI 기본 응답 (1회)
- 브라우저 콘솔 오류 확인
- API 500 오류 확인

### 변경 기능 E2E QA (해당 시)
- 생성 → 조회 → 수정 → 삭제 전체 플로우
- 새로고침 후 데이터 유지
- 검색 및 필터 동작
- 실패 처리 (네트워크 오류, 유효성 검사)
- 데스크톱 브라우저 UI (모바일은 사용자 직접 확인)

### 배포 전후 보안·회귀 QA (필수)
- 미인증 접근 차단 (302/401)
- 권한 없는 도구 실행 차단
- 개인정보·잠금 정책 유지
- 기존 기능 회귀 없음
- 활성 Worker 버전 확인

## 3. 판정 기준

| 상태 | 의미 |
|------|------|
| PASS | 실제 검증 완료, 증거 있음 |
| FAIL | 문제 발견, 수정 필요 |
| NOT TESTED | 실행하지 못함 (이유 명시) |

**금지 사항**:
- 테스트하지 않은 항목을 PASS로 표시
- HTTP 200만으로 브라우저 동작 PASS 처리
- P0/P1 미해결 상태에서 운영 배포

## 4. 실제 실행 파일 확인

MyHub는 다음 구조를 사용:
- 소스: `public/js/memo/*.js` (개별 파일)
- 번들: `public/js/memo-bundle.js` (수동 관리)
- 배포: `deploy_full.py`가 번들을 읽어 포함

**규칙**:
1. 소스 수정 시 번들도 함께 업데이트해야 함
2. `public/js/memo/inedit.js`는 **데드 코드** (사용되지 않음, 수정 금지)
3. 실제 사용 파일: `pane.js`, `composer.js`, `toolbar.js` 등
4. 번들과 소스의 일치 여부를 배포 전 확인

**경고**: 현재 번들은 수동 관리되므로 불일치 위험 있음. 자동 빌드 도입 검토 필요.

## 5. 브라우저 QA 실행 방법

### 짧은 시나리오로 분리
한 번의 긴 세션에서 모든 QA를 수행하지 말 것.

예시:
- 시나리오 A: 로그인 → 메모 저장 버튼 클릭 → 결과 확인
- 시나리오 B: 저장된 메모 수정 → 새로고침 → 유지 확인
- 시나리오 C: 테스트 데이터 삭제 → 정리 확인

### 도구 제한 사항
- 브라우저 도구가 "active tool policy"로 중단될 수 있음
- 장시간 세션(30분+)은 중단 위험 높음
- 중단 시 가능한 범위에서 API 테스트로 보완
- 브라우저 미검증 항목은 NOT TESTED로 명시

### Playwright
- 현재 미설치 (npx로 1.64.0 설치 가능)
- 브라우저 다운로드 필요 (시간 소요)
- 도입 시 스테이징 전용으로 구성
- 운영에서는 읽기 전용 테스트만 허용

## 6. 보고서 구조

### ① 개발 결과
- 변경 사항, 파일, Git SHA
- 빌드 결과, 자동 테스트 결과

### ② 브라우저 QA
| 기능 | 시나리오 | 결과 | 증거 |
|------|----------|------|------|
| ... | ... | PASS/FAIL/NOT TESTED | ... |

### ③ 상세 QA
- 정상/오류/경계 조건 시나리오
- 데스크톱 브라우저 UI, 보안 영향
- 데이터 무결성, 회귀 테스트

### ④ 발견한 문제
- 심각도 (P0/P1/P2/P3)
- 재현 조건, 원인, 수정 코드
- 재검증 결과

### ⑤ 배포 검증
- 스테이징/운영 Worker 버전
- 실제 배포 Git SHA
- 인증 보호, API 상태
- 기존 데이터 유지

### ⑥ 미검증 항목
실행하지 못한 항목과 이유 명시

### ⑦ 최종 판정
- GO / NO-GO / CONDITIONAL GO
- 근거, 남은 위험, 다음 우선순위

## 7. 심각도 분류

| 등급 | 정의 | 예시 |
|------|------|------|
| P0 | 보안 결함, 데이터 손실 위험 | 인증 우회, 권한 상승 |
| P1 | 핵심 기능 장애 | 저장 실패, 로그인 불가 |
| P2 | UI 결함 (우회 가능) | 버튼 피드백 없음, 레이아웃 깨짐 |
| P3 | 사소한 문제 | 오타, 색상 미세 조정 |

P0/P1 미해결 시 운영 배포 금지.

## 8. 테스트 데이터 관리

- 스테이징: 테스트 데이터 생성 가능, 테스트 후 정리
- 운영: 읽기 전용 테스트만 허용, 데이터 생성·수정·삭제 금지
- QA 보고서에 개인정보, 세션 쿠키, API 키 포함 금지

## 9. QA 책임 강화 (2026-10-12, GPT 24차)

### 기본 원칙
1. 첫 시도 실패를 작업 불가능으로 간주하지 않는다.
2. 설정 오류는 직접 수정하고 재실행한다.
3. 테스트 환경이 없으면 허용된 도구로 구축한다.
4. 문제가 발생하면 원인을 분석하고 해결 가능한 범위에서 바로 수정한다.
5. 수정한 기능은 실제 동작까지 확인한다.

### NOT TESTED 기준
`NOT TESTED`는 허용된 도구와 합리적인 대안을 확인한 뒤에도 실제 실행이 불가능한 경우에만 사용한다.

필수 포함 내용:
- 어떤 테스트를 수행하지 못했는가?
- 어떤 명령과 방법을 실제로 시도했는가?
- 정확한 실패 지점은 무엇인가?
- 어떤 대체 수단을 검토하고 실행했는가?
- 왜 남은 허용 수단으로도 테스트가 불가능한가?

### 테스트 구분
- **단위 테스트**: Jest로 실행, Mock 사용 가능
- **통합 테스트**: 실제 DB/서비스 코드 실행
- **Worker 통합 테스트**: 실제 Cloudflare Worker + D1 + 인증
- **브라우저 QA**: 실제 브라우저에서 사용자 행동 검증
- **API 테스트**: HTTP 요청/응답 검증

각 테스트의 검증 범위를 명확히 구분하고, 하위 단계 테스트를 상위 단계 완료로 보고하지 않는다.

### 모바일 QA
모바일 QA는 Muse의 의무 테스트에서 제외한다. 사용자가 추후 직접 진행한다.
데스크톱 브라우저 QA는 필수이다.

## 10. 운영 배포 승인 기준 강화 (2026-10-12, GPT 27차)

### 조건부 GO의 효력
조건부 GO는 모든 필수 조건이 실제로 통과해야 효력이 발생한다.

**필수 조건 중 하나라도 NOT TESTED라면 운영 배포를 진행하지 않는다.**

### 운영 배포 전 필수 확인
- 필수 보안 테스트에 NOT TESTED 없음
- 필수 회귀 테스트 PASS
- 스테이징 브라우저 QA PASS
- 실제 배포 코드 검증 PASS
- 운영 DB 호환성 PASS
- P0/P1 미해결 결함 없음
- 배포 후 운영 Smoke QA 실행 가능

### 금지 사항
- 테스트 결과를 PASS로 임의 변경
- 로컬 테스트 결과로 스테이징 필수 검증 대체
- GO 조건 중 NOT TESTED 항목이 있는데도 배포 진행
- GPT가 별도로 검증 범위를 조정하지 않은 경우의 예외 적용

### 위반 시 조치
조건을 충족하지 않고 배포한 경우:
1. 즉시 운영 상태 확인
2. 누락된 검증 완료
3. 문제 발견 시 안전한 비활성화 또는 수정
4. QA 정책 위반 재발 방지
