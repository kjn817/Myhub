## 검증 방법 (공통)

- 라이브 실증은 **이 검증이 만든 일회용 잠긴 메모**로만 수행했다. 매회 고유 토큰
  (`TRACKE…`, 비밀값 아님 — 일회용 메모 식별용 무작위 문자열)을 본문에 넣고,
  일치 여부는 프로세스 내부 해시/문자열 비교로만 판정했다.
- **사용자의 기존 잠긴 메모 (133·134·200·201)는 열람하지 않았다.** 백업 인벤토리
  확인에서 "잠긴 행 4건·전부 `ENC:` 접두"라는 집계만 확인했다 (본문 미열람).
- 일회용 메모·블록·첨부는 검증 종료 시 API로 삭제했고, D1에서 행 소멸을 확인했다
  (메모 총수는 검증 창 동안 병행 트랙들의 일회용 메모로 28↔30 변동 후 28로 복귀).
- 세션은 기존 `.scratch/` 스크립트와 같은 OTP 단회 흐름 (요청 → D1에서 코드
  조회 → 1회 검증)으로 발급받았다. **세션 값·OTP 코드·PIN 값은 이 문서와
  보고 어디에도 남기지 않았다.** 시도한 오답 PIN은 조사자가 생성한 무작위
  6자리 (사용자 PIN 아님)다.
- 로그인 세션의 `method`는 `otp`였다 (OTP 검증 직후 발급). 일상 사용 세션
  (`method=pin`)과의 차이는 §1 비고와 §3에 분리해 기록했다.

## ① 세션 단독으로 가능한 / 불가능한 것 (확정 표)

전제: **유효한 세션 쿠키 1개만 보유, PIN 재입력 없음.** 잠긴 일회용 메모
(D1 원시 상태: `is_locked=1`, 본문 `ENC:` 접두, 평문 토큰 없음 — 잠금 직후
D1 직접 조회로 확인)를 대상으로 했다.

### 가능한 것 (실증됨)

| # | 행위 | 실증 방법 | 결과 |
|---|------|----------|------|
| E-1 | **잠긴 메모 단건 본문 읽기** | `GET /api/memo/:id` (세션만) | **200, 복호화된 평문이 원문과 정확히 일치** (해시 일치). `is_locked=1`인 채로 본문이 평문으로 반환됨 |
| E-2 | **잠긴 메모 본문을 목록에서 읽기** | `GET /api/memo?limit=200` (검색어 없음) | **200, 일회용 메모가 복호화된 평문으로 목록에 포함** (정확히 일치) |
| E-3 | **잠긴 첨부파일 본문 읽기** | 일회용 파일 업로드 → 파일 잠금 (D1 `is_locked=1`) → `GET /api/memo/files/:fileId/content` (세션만) | **200, 복호화된 파일 내용이 원문과 정확히 일치** |
| E-4 | 잠긴 메모 본문 **덮어쓰기** | `PUT /api/memo/:id` (세션만, 편집문) | 200. 저장은 `ENC:`로 유지되나 (D1 확인), 이후 단건 GET에서 **편집된 새 평문**이 그대로 읽힘 — 즉 세션만으로 잠긴 메모 내용을 교체·열람 가능 |
| E-5 | 잠금 걸기 / 민감도 변경 / 메모 삭제 | `POST /:id/lock {locked:true}`, `POST /:id/sensitivity`, `DELETE /:id` (전부 세션만) | 전부 200. 삭제는 D1 행 소멸까지 확인 (파괴 행위에도 PIN 없음) |
| E-6 | **암호화 백업 발급 + 복호화** | `POST /api/backup/encrypted` (세션만, 백업 암호는 조사자가 임의로 정한 1회용 값) → 로컬에서 PBKDF2/AES-GCM 복호화 | 200, 복호화 성공. 내용: 잠기지 않은 메모 24건은 **평문 전문 포함**, 잠긴 4건은 `ENC:` 암호문 그대로 (평문 토큰 없음 확인), `auth_pins` 1행 (`pin_hash`·`pin_salt`·`iterations` 포함 — §2 오프라인 공격 경로 참조), `google_integrations` 1행 (토큰 필드는 `ENC:` 접두 — 백업만으로 사용 가능한 Google 토큰은 아님), 그 외 일정·할 일·AI 대화 등 32개 테이블 전체 |
| E-7 | 본인 정보 조회 | `GET /api/auth/me` | 200 (`hasPin: true` 포함) |

**요지: 세션 쿠키 탈취 = 잠긴 메모를 포함한 사실상 전체 데이터의 읽기·쓰기·
삭제·내보내기가 가능하다. 잠금(서버 측 AES-GCM)과 PIN step-up이 막는 것은
"해제(평문화) 행위"뿐이며, 읽기 경로는 소유자 복호화로 열려 있다.** 이는
설계상 의도된 현 정책 (소유자 세션 읽기 허용) 그대로의 동작이지만, 세션
탈취 시나리오에서는 잠금이 기밀성 장벽으로 기능하지 않는다는 사실이 실증됐다.

## ② PIN · 세션 파라미터 사실 표

### PIN 해시 (코드 `src/modules/auth/routes.ts` + 마이그레이션 0043·0045 + 운영 D1 실측)

| 항목 | 사실 | 근거 |
|------|------|------|
| PIN 형식 | 숫자 6자리 (`/^\d{6}$/`) — 경우의 수 **10⁶** | `isValidPin()` |
| 해시 알고리즘 | **PBKDF2-HMAC-SHA-256** | `hashPassword()` (PIN은 `hashPin()`이 공용 구현 재사용) |
| **반복 횟수** | **100,000회** | 코드 상수 `PBKDF2_ITERATIONS = 100_000`. **운영 D1 실측도 100,000** (`auth_pins.iterations`), 백업 안의 행도 100,000. **GPT가 말한 "PBKDF2 10만 회"와 실제가 일치함** |
| 솔트 | PIN 행마다 무작위 **16바이트** (CSPRNG `crypto.getRandomValues`), base64 24자로 해시와 함께 저장 | 코드 `hashPassword()`; 운영 D1에서 `length(pin_salt)=24` 실측 |
| 해시 출력 | **256비트 (32바이트)**, base64 44자 | `deriveBits(..., 256)`; 운영 D1에서 `length(pin_hash)=44` 실측 |
| 검증 방식 | 저장된 행의 `iterations`를 그대로 사용 (상수가 바뀌어도 구 행은 구 횟수 유지, PIN 재설정 시에만 갱신), 상수 시간 비교 | `verifyPassword()` |
| 평문 저장 | 없음. 저장 컬럼은 `pin_hash`·`pin_salt`·`iterations`뿐 (0043) | 마이그레이션 0043 |
| 온라인 잠금 | 실패 **5회 → 15분 (900초) 잠금**. D1 원자 카운터 (0045, `fail_count`/`locked_until`, 게이트 선점 방식이라 동시 버스트도 전부 카운트). **단, 잠금 중에도 정답 PIN은 성공** (소유자 차단 방지 설계) — 잠금은 오답 추측 속도만 묶는다 | `PIN_FAIL_LIMIT=5`, `PIN_FAIL_WINDOW_SEC=900`, pin-login 구현 |
| 온라인 속도 제한 | pin-login: 발신자(IP)별 10회/시간 + 전역 100회/시간. 잠금 해제 PIN 시도: 전역 10회/시간 | `checkRateLimitForIp`/`checkRateLimit` 호출부 |
| 운영 카운터 현재값 | `fail_count=0`, 잠금 없음 (실측 시점) | 운영 D1 조회 (값이 아닌 상태만 기록) |

**오프라인 공격에 대한 평가 (사실 + 추정 분리):**
- 사실: 공격자가 `auth_pins` 행 (해시·솔트·반복 횟수)을 얻으면 온라인 잠금·
  속도 제한이 전혀 적용되지 않는다. 그런 행을 얻을 현실적 경로가 **E-6으로
  실증됐다** — 탈취 세션으로 암호화 백업을 발급하면 백업 암호는 공격자가
  정하므로, 복호화된 백업 안에 PIN 해시 행이 그대로 들어 있다.
  (세션 탈취 → 백업 발급 → PIN 해시 확보 → 오프라인 추측 → PIN 확정 시
  정당한 해제 경로까지 열리는 연쇄.)
- 사실: 솔트 (16바이트, 행마다 다름)는 레인보우 테이블·사전 계산을 막지만,
  후보 공간 자체가 10⁶뿐이라 솔트 유무와 무관하게 전수 추측이 가능하다.
- 추정 (실측 아님): PBKDF2-HMAC-SHA256 100,000회 기준 고성능 GPU의
  추측 속도는 공개 벤치마크 (hashcat 계열) 수준에서 대략 초당 10⁴~10⁵개
  오더로, 전 공간 10⁶개는 **분 단위 오더**, 평균은 그 절반으로 추정된다.
  실제 GPU로 측정하지 않았으므로 수치 자체는 NOT MEASURED로 남긴다.
  방향성 (100,000회로는 6자리 공간을 오프라인에서 지킬 수 없다)은
  추정치의 세부 수치와 무관하게 성립한다.

참고 — 백업 파일 자체의 KDF도 PBKDF2-SHA256 **100,000회** + AES-256-GCM
(`src/modules/backup/routes.ts`). 단 백업 암호는 사용자가 정하는 8자
이상 임의 문자열이라 PIN과 후보 공간이 다르다.

참고 — 메모 본문 암호화는 AES-256-GCM (IV 12바이트 무작위, `ENC:` 접두,
키는 Worker Secret `MEMO_ENCRYPTION_KEY`). **종단간 암호화가 아니다** —
서버가 소유자 세션 요청에 복호화해 주는 구조라, E-1이 성립하는 이유다.

### 세션 (코드 `src/modules/auth/routes.ts`, `src/index.ts` + 라이브 실측)

| 항목 | 사실 | 근거 |
|------|------|------|

| 유효기간 | **30일 고정** (발급 시점 `exp`, 사용에 따른 연장·유휴 만료 없음) | `SESSION_TTL_MS = 30일`; 라이브 토큰 잔여 약 30.0일 실측 |
| 쿠키 플래그 | `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000` (Domain 없음 = host-only) | 라이브 `Set-Cookie` 속성 실측 + 코드의 쿠키 문자열 |
| 무효화 방식 | D1 `session_versions` 카운터 (0051). 로그아웃·PIN 재설정 시 버전 +1 → **이전 전 토큰 일괄 무효**. 토큰 개별 무효화 수단 없음. 버전 조회 실패 시 세션 거부 (fail-closed) | `bumpSessionVersion()`/`verifySessionForEnv()` |
| 탈취 토큰의 사용 범위 | IP·UA 바인딩 없음, 동시 사용 감지 없음 — 유효한 토큰은 어디서든 만료 (30일) 또는 버전 bump 전까지 사용 가능 | 검증 로직에 해당 검사 부재 (코드 전수 확인) |
| 발급 수단 구분 | `method`: `otp` (OTP 검증) / `pin` (PIN 로그인·PIN 재설정 직후 재발급). set-pin의 step-up 판정에만 쓰임 (C-1) | `SessionMethod` |
| 인증 미들웨어 | `/api/auth/*`·`/api/health`·로그인 에셋·채널 웹훅·`POST /api/mcp` (자체 인증) 외 전 경로가 세션 검사 뒤에 있음. 무효 세션은 API 401 / 페이지 로그인 리다이렉트 | `src/index.ts` 미들웨어; N-5 실증 |

### OTP (세션 발급 경로, 참고 사실)

| 항목 | 사실 |
|------|------|
| 코드 | 숫자 6자리, 유효 **10분**, 검증 성공 시 원자적 1회 소비 (재사용 불가) |
| 시도 제한 | 코드당 오답 5회 (단 정답은 횟수와 무관하게 성공 — 소진 DoS 방지), 요청 IP별 5회/시간·전역 20회/시간, 검증 IP별 20회/시간·전역 100회/시간 |

## ③ 제안 (구현하지 않음 — 선택지 기록만)

아래는 이 트랙에서 **구현하지 않았다.** 우선순위·채택은 후속 결정 사항이다.

1. **잠긴 메모 읽기에 step-up 요구 (읽기 step-up)**
   - 내용: 단건 GET·목록·첨부 content가 잠긴 메모를 복호화하기 전에 PIN
     재입력 (또는 시간 제한 있는 "승격" 상태 — 예: PIN 확인 후 5~10분간만
     복호화 허용하는 플래그를 세션 버전에 결합)을 요구한다.
   - 근거: E-1~E-3 실증 — 현 구조에서 잠금은 세션 탈취에 기밀성 장벽이
     되지 못한다. 해제 step-up만으로는 GPT 지적대로 읽기 보호가 안 된다.
   - 비용: 소유자 본인의 일상 열람에도 마찰이 생긴다 (아내와 함께 쓰는
     시스템이라는 전제와 충돌 가능). 시간 제한 승격 방식이 절충안.

2. **백업 발급에 step-up + 백업 범위에서 인증 자료 제외**
   - 내용: (a) `POST /api/backup/encrypted`에 PIN step-up을 걸거나,
     (b) `auth_pins`를 백업 대상에서 제외 (PIN은 복원 대상이 아니라
     재설정이 정답 — `session_versions`를 제외한 것과 같은 논리),
     (c) `google_integrations`도 같은 검토.
   - 근거: E-6 + §2 연쇄 — 세션 탈취가 PIN 오프라인 공격 재료로
     이어지는 유일한 실증 경로가 백업이다. 백업의 복원 가치와 무관한
     행 (PIN 해시)이 가장 위험한 산출물이다.

3. **PIN 해시에 서버 측 페퍼 (pepper) 추가**
   - 내용: 저장 해시를 `PBKDF2(pin, salt)`에서
     `HMAC(Worker Secret 페퍼, PBKDF2(pin, salt))` 형태로 바꿔, D1·백업이
     유출돼도 Worker Secret 없이는 오프라인 검증 자체가 불가능하게 한다.
   - 근거: 반복 횟수를 올려도 (예: OWASP 권고 수준 600,000회 = 6배)
     10⁶ 공간에서는 선형 개선에 그친다. 페퍼는 공격 전제 자체를
     (해시 + 서버 비밀 동시 유출로) 바꾼다. 반복 횟수 상향과 병행 가능.
   - 대안: PIN 자릿수 확대 (8자리 = 10⁸) — 페퍼 없이도 오프라인
     시간을 100배로 늘리지만 입력 마찰이 커진다.

4. **패스키 (WebAuthn) 를 step-up·로그인 수단으로 추가**
   - 내용: 플랫폼 인증기 (Face ID·지문·Windows Hello)를 잠금 해제와
     PIN 재설정의 step-up으로 허용하고, 장기적으로 로그인 1요소로 승격.
     PIN은 폴백으로 유지.
   - 근거: 피싱·탈취에 강하고 오프라인 무차별 대입 대상이 없으며
     (공개키 방식), iPhone 실사용 환경과 잘 맞는다. GPT가 검토를 권고한
     항목이다. 구현 시 D1에 자격증명 테이블 + 챌린지 발급/검증 라우트가
     필요하고, 등록·복구 흐름 (기기 분실 시 OTP 폴백) 설계가 선행돼야 한다.

5. **`method='otp'` 세션의 권한·수명 분리**
   - 내용: OTP 세션은 PIN 설정 목적에 한정한 단수명 (예: 1시간) 토큰으로
     발급하고, 일반 앱 사용은 `pin` 세션 또는 별도 교환 절차를 거치게 한다.
   - 근거: C-1 — OTP 세션 탈취 시 PIN 교체까지 닿는 비대칭이 여기서
     생긴다. OTP 세션의 30일 수명은 그 목적에 비해 과하다.

## NOT TESTED / 한계

- **C-1의 라이브 실증**: 하지 않았다 (의도적). 실증 = 사용자 실제 PIN
  교체라 검증 행위가 곧 사고가 된다. 코드 경로는 전수 확인했다.
- **`method='pin'` 세션의 set-pin 403 라이브 확인**: PIN 로그인은 사용자
  PIN 값을 알아야 해 조사자가 수행할 수 없다 (값을 묻거나 쓰지 않는 것이
  원칙). 코드로만 확정.
- **오프라인 추측 속도**: 실제 GPU 실측 없음 — §2에 추정치로 분리 표기.
- **해제 PIN 속도 제한 소진 (전역 10회/시간) 도달 여부**: 제한을 실제로
  소진시키면 사용자 본인의 정당한 해제까지 막을 수 있어 시도하지 않았다.
  오답 1회에서 403 `PIN_INVALID`까지만 확인.
- **AI 채팅 노출 여부**: 비결정적 경로라 1회 실증 + 코드 경계 (N-7)로
  근거를 댔다. 반복 실증은 다른 트랙 (인젝션 시나리오) 범위.
- **브라우저 저장소·XSS 경유 토큰 탈취 자체**: 이 트랙은 "탈취 이후"
  시나리오만 다뤘다. 쿠키가 `HttpOnly`라 스크립트 직접 읽기는 막히지만,
  XSS가 있으면 동일 출처 요청 대행은 가능하다 — 그 벡터의 존재 여부는
  프론트엔드 보안 트랙 범위.
- 기존 잠긴 메모 4건의 **내용**은 어떤 경로로도 읽지 않았다 (집계만 확인).
