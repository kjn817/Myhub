- 범위: 메모 잠금의 편집(PUT)·해제 경로 서버 측 회귀·강제 실증. 클라이언트(public/)는 트랙 D 영역이라 건드리지 않음. 커밋·배포 없음.

## 해제 경로 전수 열거 (코드 기준)

잠금 상태를 바꾸는 쓰기는 `src/modules/memo/routes.ts`에만 존재한다 (`SET is_locked`·`locked_blocks` 변경 전수 grep 확인). AI 도구 경로(`memo-tools.ts`)는 잠긴 메모의 수정·삭제를 거부하고, 백업 복원은 원시 행(암호문) 그대로라 해제 경로가 아니다. 일괄 해제·자동 해제 경로는 **존재하지 않는다**.

| # | 경로 | 종류 | PIN 게이트 조건 |
|---|------|------|-----------------|
| U1 | `POST /api/memo/:id/lock` `{locked:false}` | 메모 본문 해제 | 현재 잠긴 메모일 때만 |
| U2 | `POST /api/memo/:id/unlock-block/:blockId` | 블록 해제 (복호 html을 응답으로 반환) | 블록이 존재하면 항상 |
| U3 | `POST /api/memo/files/:fileId/lock` `{locked:false}` | 첨부 해제 (복호→재업로드) | 현재 잠긴 파일일 때만 |

공통 게이트 `checkUnlockPin` (routes.ts): PIN 미설정 계정(auth_pins 행 없음 / 테이블 없음)은 lockout 방지를 위해 면제, 손상된 PIN 행은 500, PIN 없음→403 `PIN_REQUIRED`, 오답→403 `PIN_INVALID`, 제출 시도는 전역 속도 제한 10회/시간. 게이트 실패 시 어떤 DB 쓰기보다 먼저 거부된다.

## 발견한 결함 / 관찰

- **신규 결함 없음.** 이번 트랙 범위(편집·해제 서버 경로)에서 수정이 필요한 결함은 발견되지 않았다 — bdc3f1d의 fail-closed·PUT 잠금 인지·step-up 적용이 런타임과 라이브 양쪽에서 유지되고 있음을 실증했다.
- 관찰 1 (기존 의도된 동작, 판단 보류): U2에서 `locked_blocks` 제거 UPDATE가 실패하면 `{ok:true, html, warning:'unlock_pending'}`으로 복호된 html을 반환하면서 암호문 블록이 DB에 남는다. PIN 검증을 통과한 소유자에게만 반환되므로 노출 범위는 소유자 본인이지만, "해제됐다"는 응답과 DB 상태가 어긋날 수 있다. 클라이언트 측 처리(트랙 D)와 맞물려 있어 이 트랙에서는 변경하지 않고 기록만 남긴다.
- 관찰 2 (범위 밖): 존재하지 않는 메모 id에 대한 PUT은 0행 UPDATE에도 `{ok:true}`를 반환한다 (잠금과 무관한 기존 동작).

## NOT TESTED (정직 표기)

- **라이브 올바른 PIN 해제 (U1·U2·U3)**: 사용자의 실제 PIN 값을 다루지 않는다는 원칙상 라이브에서는 실시하지 않았다. 런타임에서 테스트 PIN으로 전 경로 실증 완료.
- **U3 정상 왕복 (실제 Cloudinary 파일 복호→재업로드→잠금 해제 완료)**: 런타임은 Cloudinary가 없고, 라이브는 올바른 PIN이 필요해 미실시. 게이트·fail-closed까지만 실증.
- **라이브 fail-closed (키 소실 상황)**: 운영 키 환경을 깨는 행위는 하지 않는다. 런타임(키 없음 env)으로 대체 실증.
- **PIN 속도 제한 (10회/시간) 라이브 동작**: 오답 시도를 라이브에서 반복하면 실제 사용자의 해제 시도를 막을 수 있어 미실시. 런타임 오답 케이스에서 제한 경로 코드는 통과하나, 한도 초과 429 자체는 별도 실증 없음.
