# MSW(HTTP 레벨 API 모킹) 적용 기록 — 2026-10-27

`docs/github-test-ai-research-20261027.md` 1순위 MSW 항목(★18,311·MIT)의 패턴 확립.
`global.fetch = jest.fn()`은 응답만 흉내 내고 호출 자체(URL·헤더·바디 파라미터)의
오류는 잡지 못한다. MSW는 실제 fetch 호출 형태를 유지한 채 응답만 가로채므로,
호출 형태가 성질인 테스트에서 잘못된 파라미터·빠진 헤더를 잡는다.

## 설치

- `msw@2.15.0`을 devDependency로 추가 (`npm install --save-dev msw@2`).
  프로덕션 의존성 추가 없음.
- **v2를 쓴 이유 — v3는 이 저장소에서 쓸 수 없다.**
  v3.0.3은 ESM 전용(`"type": "module"`, CJS 빌드 없음). 이 저장소의 Jest는
  ts-jest CJS 변환 환경이라 `require('msw')`가 실패한다. Jest 30의
  require(esm)은 `NODE_OPTIONS=--experimental-vm-modules`가 있어야 동작하는데,
  그 플래그는 `npx jest` 기본 실행에 포함되지 않아 전수 실행이 깨진다.
  v2는 CJS 빌드(`lib/node/index.js`)를 제공해 플래그 없이 동작한다.
- v2의 CJS 빌드도 ESM 전용 전이 의존성(`rettime`·`until-async`·`@open-draft`)을
  require하므로, `jest.config.js`에서 해당 패키지만 ts-jest로 CJS 변환한다
  (`transform` + `transformIgnorePatterns`). msw/`@mswjs` 본체는 변환 대상이 아니다.

## 헬퍼

`tests/helpers/msw-server.ts` — `createMswServer(...handlers)`:

- `beforeAll`에서 `server.listen({ onUnhandledRequest: 'error' })` —
  핸들러가 없는 URL로 fetch가 나가면 테스트가 실패한다. 프로덕션 코드가
  예상 밖 URL을 부르는 것을 잡는 것이 목적이다.
- `afterEach`에서 `resetHandlers()` — 테스트 안에서 `server.use()`로 바꾼
  핸들러를 격리한다. `afterAll`에서 `close()`.

사용법:

```ts
import { createMswServer, http, HttpResponse } from './helpers/msw-server'

const server = createMswServer(
  http.post('https://api.exa.ai/search', async ({ request }) => {
    // 핸들러가 요청을 검사한다 — 이 단언이 MSW로 바꾼 의미다.
    expect(request.headers.get('x-api-key')).toBe('test-key')
    const body = (await request.json()) as any
    expect(body.category).toBe('news')
    return HttpResponse.json({ results: [] })
  }),
)

// 테스트 안에서 응답만 바꿀 때 (기본 핸들러의 요청 검사는 유지되지 않음):
server.use(http.post('https://api.exa.ai/search', () =>
  HttpResponse.json({}, { status: 500 }),
))
// 네트워크 실패 흉내:
server.use(http.post('https://api.exa.ai/search', () => HttpResponse.error()))
```

핸들러 안 단언이 실패하면 해당 fetch가 그 expect 오류로 reject된다.
호출자가 fetch 오류를 자기 에러로 감싸는 경우(예: `searchNews` →
`NewsSearchError`) 테스트는 감싼 에러로 실패한다 — 실패 자체는 보장되나
메시지가 한 겹 감싸지므로, 원인 확인 시 핸들러 단언을 먼저 볼 것.

## 언제 MSW를 쓰고 언제 fetch mock을 써도 되는지

| 경우 | 방식 |
|---|---|
| 호출 형태(URL·쿼리·헤더·바디)가 성질 | **MSW** — 핸들러에서 요청 검사 단언 필수. 검사 단언이 없으면 교체하지 않는다 |
| 함수가 `fetchFn`을 인자로 받아 주입하는 단위 테스트 (라우팅·필터·체인 로직) | 기존 주입 mock 유지 — MSW 대상이 아니다. `fetchNewsSources` 체인 테스트가 여기에 해당 |
| 응답 매핑·에러 분기만 보는 테스트 | 기존 mock 유지 가능. 단, 같은 파일에 MSW 서버가 있으면 `server.use()`로 응답을 바꾸는 쪽이 일관된다 |
| `global.fetch`를 통째로 교체하는 `jest.spyOn(global, 'fetch')` | MSW와 같은 파일에 섞지 않는다 — MSW가 패치한 fetch를 스파이가 덮어버린다 |

  (tsconfig `include`가 `src`만 포함). 타입은 ts-jest 변환 시점에 검사된다.
