# 모듈형 데스크톱 워크스페이스 — 1차 구현 설계 확정

- 날짜: 2026-10-30 · 상태: 설계 확정 (구현 전). 결정 변경은 별도 개정 기록이 필요하다.
- 대상: 새 셸 페이지 `/desktop.html` 추가. 기존 홈·네비게이션은 무변경, 진입 링크만 추가한다.

## 1. 목적·배경

GPT 재평가(2026-10-30)에서 제품 완성도가 3.5/10으로 최대 감점을 받았다.

> "모듈형 데스크톱 워크스페이스는 아직 미착수이며, 창 배치·크기 조절·상태 복원과
> 같은 핵심 기능은 구현되지 않았다."

현재 MyHub는 페이지 단위 이동이 기본이다. 메모를 보면서 일정을 확인하려면
페이지를 오가야 하고, 이전 화면의 스크롤·입력 상태는 그때마다 끊긴다.
1차 구현의 목적은 기존 페이지를 고치지 않고 그 위에 창 관리 셸을 얹어,
한 화면에서 여러 모듈을 동시에 열고·옮기고·크기를 조절하고·새로고침 후에도
배치를 복원하는 경험을 제공하는 것이다.

성공 기준: ① 드래그로 창 이동 ② 모서리·변 드래그로 크기 조절
③ 새로고침·재방문 후 창 구성·배치 복원 ④ 모듈 4종 동시 표시·포커스 전환.

## 2. 1차 범위 / 비범위

### 범위

- 새 셸 페이지 `/desktop.html`과 전용 CSS·JS 3파일.
- 모듈 4종을 창으로 여는 창 모델 (이동·리사이즈·포커스·최소화·닫기).
- 하단 작업 표시줄 (열린 창 목록·복원·포커스).
- `localStorage` 기반 상태 저장·복원.
- 모바일 폴백 (폭 768px 미만 전체화면 렌더링).
- 공용 상단바(`public/nav.js`)에 데스크톱 진입 링크 추가.
- `scripts/static-assets.json`에 신규 정적 자산 등록.

### 비범위 (1차에서 하지 않는다)

- 기존 페이지(`/memo.html` 등)의 내부 구조·기능 변경.
- 서버 동기화, 기기 간 배치 공유.
- 창 스냅·타일링, 최대화, 다중 데스크톱.
- 모듈을 컴포넌트로 재작성하는 작업.
- 모바일에서의 다중 창 동시 사용.
- 창 간 데이터 연동 (딥링크·드래그 전달 등).

비범위 항목은 11절 확장 목록에서 다룬다. 범위 변경은 구현 전 문서 개정으로만 한다.

## 3. 파일 구조 (500줄 규칙)

| 파일 | 역할 | 비고 |
|---|---|---|
| `public/desktop.html` | 구조만 (셸·작업 표시줄 마크업) | 인라인 스크립트 금지 |
| `public/css/desktop.css` | 셸·창·작업 표시줄 스타일 | 500줄 이하 |
| `public/js/desktop/state.js` | 상태 모델, 순수 로직 | `window.MyHubDesktopState` |
| `public/js/desktop/windows.js` | 창 DOM 생성·관리 | `window.MyHubDesktopWindows` |
| `public/js/desktop/main.js` | 부트스트랩, 이벤트 연결 | 위 두 모듈 조립만 |

원칙: `state.js`는 DOM을 만지지 않는다(테스트는 이 파일만으로 완결).
`windows.js`는 상태를 직접 변형하지 않고 `state.js` 함수를 통해서만 바꾼다.
프레임워크 없이 바닐라 JS. 정적 자산은 `scripts/static-assets.json`에 등록해야
ASSETS 바인딩으로 서빙된다 — 등록 누락 시 배포해도 404이므로 체크리스트에 포함한다.

## 4. 모듈 정의

| 모듈 id | 페이지 | 기본 크기(안) |
|---|---|---|
| `memo` | `/memo.html` | 880×620 |
| `schedule` | `/schedule.html` | 880×620 |
| `todo` | `/todo.html` | 640×560 |
| `chat` | `/chat.html` | 720×620 |

- 모듈당 창 1개 싱글턴이다. 이미 열려 있으면 새 창을 만들지 않고 해당 창을
  복원(최소화 해제)하고 포커스만 이동한다.
- 기본 위치는 화면 중앙 기준 계단식 오프셋 적용 후 clamp한다.
- 모듈 목록은 `main.js` 상수 1곳에만 둔다. 모듈 추가 시 스키마는 불변이다.

## 5. 창 상태 모델

### 5.1 스키마

저장 키: `myhub.desktop.v1`

```json
{
  "version": 1,
  "windows": [
    { "id": "memo", "module": "memo", "x": 40, "y": 32,
      "w": 880, "h": 620, "z": 3, "minimized": false }
  ],
  "activeId": "memo",
  "zCounter": 3
}
```

- `id`와 `module`은 1차에서 동일하다(모듈 싱글턴). 다중 인스턴스를 허용하는
  2차 확장을 위해 필드는 분리해 둔다.
- `x, y, w, h`는 CSS px(뷰포트 기준), `z`는 포커스 순서, `zCounter`는 마지막 발급 z 값.
- `minimized: true`인 창은 DOM에서 숨기되 iframe은 유지한다(8절).

### 5.2 불변 규칙

- 상태 모델의 모든 함수는 입력 상태를 변형하지 않고 새 객체를 반환한다.
- 저장 직전에는 항상 직렬화 가능한 순수 데이터만 남긴다 (DOM 참조 금지).
- 파싱 실패·버전 불일치·필드 타입 오류가 있으면 해당 항목을 버리고,
  복구 불가능하면 빈 상태로 시작한다. 깨진 상태가 셸 전체를 막지 않는다.

### 5.3 상태 전이

| 동작 | 전이 |
|---|---|
| 열기 | 없는 모듈이면 창 항목 추가, `z = ++zCounter`, `activeId`로 설정. 있으면 복원과 동일. |
| 포커스 | `z = ++zCounter`, `activeId` 갱신. 위치·크기 불변. |
| 최소화 | `minimized: true`. `activeId`는 남은 최상위 창으로 이동, 없으면 `null`. |
| 복원 | `minimized: false` 후 포커스와 동일. iframe 재로드 없음. |
| 닫기 | 항목 제거. iframe DOM도 함께 제거한다. `activeId` 재계산. |
| 이동 | `x, y` 갱신 후 clamp 적용. 드래그 종료 시점에 저장한다. |
| 리사이즈 | `w, h, x, y`(방향에 따라) 갱신 후 clamp 적용. 종료 시점에 저장한다. |

- 이동·리사이즈 중 매 프레임 저장하지 않는다(성능·쓰기 횟수). 드래그 중
  새로고침하면 직전 확정 배치로 돌아가는 것이 의도된 동작이다. 그 외 전이는 즉시 저장.

### 5.4 clamp 규칙

복원·이동·리사이즈 세 경로 모두 같은 clamp 함수를 거친다.

- 크기: 너비 최소 300, 높이 최소 220. 상한은 뷰포트 크기.
- 위치: 창 제목줄이 최소 48px 뷰포트 안에 남도록 `x, y`를 제한한다. 창을 화면
  밖으로 완전히 밀어 넣어 잃어버리는 경우를 원천 차단한다.
- 더 큰 화면에서 만든 상태도 복원 시 clamp를 다시 적용해 항상 조작 가능하게 한다.

## 6. iframe 채택 근거와 대안 비교

### (a) iframe — 채택

- 기존 페이지를 무수정으로 재사용한다. 메모·일정·할 일·채팅의 검증된
  화면과 로직을 그대로 쓴다.
- 페이지별 스크립트·전역 상태가 창마다 격리된다. 전역 변수 충돌,
  이벤트 리스너 중복 같은 통합 사고가 구조적으로 발생하지 않는다.
- 인증은 same-origin 쿠키로 자동 전송된다 (7절). 별도 토큰 전달이 없다.
- 단점: 창마다 초기 로드 비용이 있다. 단, keep-alive(8절)로 1회만 낸다.
- 단점: 창 간 통신이 필요하면 `postMessage`를 거쳐야 한다. 1차에는
  창 간 통신 자체가 없으므로 비용이 발생하지 않는다.

### (b) 컴포넌트 내장 — 1차 기각

- 각 페이지를 셸 안에서 동작하는 컴포넌트로 재작성해야 한다. 페이지들이 독립
  문서 전제(전역 스크립트, 페이지 단위 초기화)라 재작성 범위가 1차를 크게 초과한다.
- 기존 페이지 동작의 회귀 위험이 크고, 단독·컴포넌트 두 경로 동시 유지 부담이 생긴다.

결론: 1차는 iframe이다. 컴포넌트화는 셸의 가치가 실사용으로 확인된 뒤의
장기 과제로 남긴다.

## 7. 기존 페이지와의 상호작용

- 인증: 미들웨어가 `.html` 전체를 인증 보호한다. `/desktop.html`도,
  iframe 안의 각 페이지도 같은 보호를 받는다. iframe은 same-origin이라
  세션 쿠키가 자동 전송되며, 셸이 인증을 우회하거나 대행하지 않는다.
  세션 만료 시 iframe 안에서 로그인 흐름이 도는 것은 기존 페이지 단독
  사용과 같은 동작으로, 1차에서는 셸이 개입하지 않는다.
- 테마: 각 페이지가 자체 처리한다. 셸은 iframe 내부에 스타일을 주입하지
  않고 간섭하지 않는다. 셸 자체의 색만 디자인 규칙을 따른다 (9절).
- 진입 링크: 공용 상단바(`nav.js`)에 데스크톱 링크를 추가한다.
  로그아웃 버튼이 추가된 것과 같은 마운트 패턴을 따르며, 기존 링크와
  홈 화면 구성은 바꾸지 않는다.

## 8. 동작 세부 결정

- keep-alive: iframe은 창을 처음 열 때만 생성·로드한다. 이후 포커스
  전환·최소화·복원은 `display`/`visibility` 토글만으로 처리하고
  재로드하지 않는다. 입력 중이던 내용과 스크롤이 유지되는 것이 목적이다.
  닫기만 iframe을 제거하므로, 다시 열면 새로 로드되는 것이 맞다.
- 드래그 성능: Pointer Events 기반으로 구현하고, 이동 중에는
  `left/top`이 아닌 `transform`으로 위치를 반영한다.
- iframe 포인터 문제: 드래그·리사이즈 중에는 모든 iframe에
  `pointer-events: none`을 적용한다. iframe 위로 포인터가 들어가면
  부모 문서가 이벤트를 잃는 고전적 문제를 회피하기 위한 필수 조치다.
- 작업 표시줄: 하단 고정. 열린 창 버튼 목록, 클릭 시 복원·포커스,
  활성 창 표시. 창이 없으면 모듈 실행 버튼만 보인다.
- 모바일 폴백: 뷰포트 폭 768px 미만이면 창을 전체화면으로 렌더링한다.
  상태 저장 형식은 동일하게 유지하므로, 데스크톱에서 저장한 배치를
  모바일이 깨뜨리지 않는다. 다중 창 동시 사용은 데스크톱 전용이다.

## 9. 서버 동기화를 1차에서 제외한 근거

- 주 사용 경로는 단일 사용자·단일 기기다. 배치 복원 요구는
  `localStorage`만으로 충족된다.
- 서버 저장은 API·마이그레이션·동시 편집 충돌 규칙까지 동반하므로,
  셸 자체의 가치가 검증되기 전에 넣으면 1차 범위가 무너진다.
- 제외는 포기가 아니다. 상태 스키마에 `version`을 둔 이유가 서버
  동기화 도입 시 마이그레이션 경로를 열기 위해서다. 2차에서 기기 간
  동기화와 함께 도입한다.

## 10. 디자인

- 색: 흰색·회색·검정 기반에 파스텔 블루를 강조색으로만 쓴다.
- 아이콘: Lucide SVG만 사용한다. 이모지 금지.
- 창 프레임은 얇은 테두리와 제목줄(모듈명·최소화·닫기 버튼)로 단순하게
  유지한다. 그림자 등 장식 효과는 포커스 구분에 필요한 최소한만 허용한다.

## 11. 2차 이후 확장 목록

1. 서버 동기화: 배치 상태를 계정에 저장, 기기 간 복원.
2. 창 스냅·타일링: 화면 절반·4분할 스냅, 자동 정렬.
3. 최대화: 창 단위 전체화면 토글.
4. 모듈 추가: 브리핑 등 나머지 페이지를 모듈로 편입.
5. 모바일 다중 창: 하단 탭 전환 방식 등 모바일 전용 모델 검토.
6. 창 간 연동: 채팅에서 메모 열기 같은 딥링크, `postMessage` 프로토콜 정의.
7. 컴포넌트화: 사용 빈도가 높은 모듈부터 iframe 대체를 단계적으로 검토.

각 항목은 착수 시 별도 설계·승인을 거친다. 이 목록은 약속이 아니라 방향 기록이다.

## 12. 테스트 전략

원칙: 의미 있는 테스트만 남긴다. 검증 대상 성질이 깨지면 실패해야 하고,
카나리아(일부러 깨뜨려 잡는지 확인)를 통과해야 한다.

### 상태 모델 단위 테스트 (`state.js`)

- 직렬화 왕복: 저장→파싱 결과가 원본과 동등한지.
- 복원: 저장된 배치로 초기 상태가 재현되는지.
- clamp: 화면 밖 좌표·최소 미만 크기·뷰포트 초과 크기가 규칙대로
  보정되는지, 뷰포트가 줄어든 경우에도 제목줄 48px이 남는지.
- z-order: 포커스 반복 시 z가 단조 증가하고 `activeId`가 일치하는지,
  싱글턴 규칙(같은 모듈 재열기 시 창이 늘지 않는지)이 지켜지는지.
- 깨진 입력: 잘못된 JSON, 버전 불일치, 타입이 틀린 필드가 있어도
  예외 없이 빈 상태 또는 부분 복구로 시작하는지.
- 불변성: 전이 함수가 입력 객체를 변형하지 않는지.

### UI 배선 테스트 (jsdom)

- 모듈 버튼 클릭 → 창 DOM과 iframe이 1회만 생성되는지 (keep-alive).
- 최소화·복원·닫기가 표시 토글과 상태 전이에 정확히 연결되는지.
- 작업 표시줄 버튼이 해당 창을 복원·포커스하는지.

### 별도 단계임을 명시

- 브라우저 실동작 QA(실제 드래그 감각, iframe 내 페이지 동작, 모바일
  실기기)는 자동 테스트로 대체하지 않는다. 배포 후 실제 브라우저에서
  시나리오를 수행하는 별도 단계로 진행하고, 결과는 QA 문서에 기록한다.
- jsdom 통과를 브라우저 PASS로 보고하지 않는다.
