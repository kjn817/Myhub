> POC 측정 문서. 운영 도입 판단용 근거만 담는다. **GO/NO-GO 단정 없음** — 수치가 판단 재료다.

## 한 줄 요약

- **정확도(180판정/arm)는 세 arm이 사실상 동점** — Clairic 81.1%, GLM-4.7-flash 77.8%, llama-3.1-8b 80.6%.
  모호한 `task` 필드를 빼면 87.3% / 86.7% / 88.0%로 더 좁혀진다. 정확도는 차별점이 아니다.
- **차별점은 지연·비용·신뢰성이다.** Clairic은 호출당 230ms·7.2 뉴런으로 GLM(21.1초·39.3 뉴런)보다
  92배 빠르고 5.4배 싸다. 단, llama-8b(3.2초·3.7 뉴런)보다는 뉴런이 2배 비싸다 — 스키마 토큰이 원인이다.
- **Clairic의 진짜 강점은 상대 날짜 해석**이다 (절대 날짜는 세 arm 모두 100%, 상대 날짜는 Clairic 68.4% >
  GLM 63.2% >> llama 21.1%). 진짜 약점은 **일반명사 장소의 null 반환**(8건)과 **`task` 필드 정의**(전 arm 공통)이다.
- **GLM arm은 10%(3/30)가 무응답 catastrophic failure**다 — 2,000 토큰 추론 예산을 다 쓰고 빈 답을 냈다.
  이 3건을 빼면 GLM 정확도는 85.8%로 가장 높다. 즉 GLM의 문제는 부정확이 아니라 **신뢰성**이다.
- **confidence 임계값은 정밀도를 크게 못 올린다.** t=0.5→0.9에서 정밀도 96.5%→98.1% (+1.6pp)에
  재현율 82.1%→76.9% (−5.2pp). 고신뢰 오답(≥0.99)이 2건 존재한다. 결합 규칙(아래 §6)이 현실적이다.

## 2. 방법

### 2.1 평가셋 — `tests/fixtures/clairic-ab/eval-set.json`

- 합성 메모 **30건 (한국어 15 + 영어 15)**, 전부 가상 인물·금액·장소. 실데이터·잠긴 메모 없음.
- 필드 6개 (모든 메모 동일): `person`(text) · `event_date`(date) · `event_time`(time) ·
  `amount`(number) · `task`(text) · `place`(text). 필드별 정답은 값 또는 `null`.
- 필드 존재 비율: person·event_date 30/30, event_time 18/30, amount 18/30, task 14/30, place 24/30.
  즉 **판정 180건 중 존재 134건·부재 46건** — `null` 판정도 함께 잰다.
- 기준 날짜 2026-10-28(수). "내일·모레·금요일·tomorrow·next Monday" 같은 상대 날짜는 이 날짜 기준.
  기준 날짜 문장을 양 arm에 동일하게 state/prompt 앞에 붙였다 (실제 메모 저장 시 `created_at`이 같은 역할을 한다).
- 채점 규칙: date는 ISO 정확 일치, time은 HH:MM(24h) 정확 일치, amount는 숫자 정확 일치,
  text는 문자 단위 F1 ≥ 0.5 (정규화: 소문자·문자/숫자만). null은 예측 null과 정답 null이 일치해야 정답.
  - 민감도 분석: text를 포함(containment) 규칙으로 바꿔도 순위는 안 바뀐다
    (Clairic 81.1→81.7%, GLM 77.8→77.2%, llama 80.6→81.7%). F1 임계값이 결론을 좌우하지 않는다.

### 2.2 비교 arm — "현행 LLM 추출"의 정직한 정의

**MyHub에는 연결된 LLM 추출기가 없다.** `memory.llm_extract_enabled` 플래그는 OFF이고,
`captureFacts`의 `llmExtract` 주입점은 어떤 운영 호출자도 채우지 않는다
(`src/services/fact-graph.ts`, `src/modules/memory/routes.ts` 확인).
그래서 LLM arm은 "운영 추출기"가 아니라 **같은 필드 계약으로 돌린 대표 Workers AI LLM**이다.
Gemini는 측정하지 않았다 — Gemini 키는 시크릿이라 다루지 않는다 (과제 제약).

| arm | 모델 | 프롬프트/호출 | 비고 |
|---|---|---|---|
| clairic | `@cf/cloudflare/clairic` | `state` + 6개 typed `fields`, 지침 포함 | 한 번의 forward pass |
| llm | `@cf/zai-org/glm-4.7-flash` | 동일 필드 목록을 JSON 스키마로 지시, temperature 0, max_tokens 2000 | **Thinking 모델** — 추론 토큰이 답보다 많다 |
| llm-fast | `@cf/meta/llama-3.1-8b-instruct-fp8` | 동일 프롬프트, temperature 0, max_tokens 400 | 감도 체크용: 빠르고 추론 없는 LLM |

현행 기본 경로(결정적 `extractFacts`)는 typed 필드를 내놓지 않아 동일 채점이 안 된다.
대신 Jest로 **핵심 사실 문장 회수율**을 쟀다: **1.00 (48/48, KO 1.00 / EN 1.00)** —
`tests/unit/clairic-ab-deterministic.test.ts` (회귀 하한 0.6).
즉 지금 기본 경로는 짧은 메모의 문장을 빠짐없이 뽑지만, "날짜를 ISO로·금액을 숫자로·없으면 null로"
라는 typed 추출은 하지 못한다. Clairic이 메우는 격차는 정확히 그 부분이다.

### 2.3 전송 경로 — REST 401 → 일회용 스크래치 Worker

- 연결된 Cloudflare API 토큰으로 Workers AI REST(`/ai/run`)를 직접 호출하면
  **401 code 10000 "Authentication error"**가 난다. 계정 GET은 같은 토큰으로 성공하므로
  토큰 자체가 아니라 **Workers AI REST 스코프 부재**로 판정했다 (llama 모델로도 동일 401 재현).
- 그래서 RSS 트랙과 같은 방식 — **일회용 스크래치 Worker**(`clairic-ab-probe-20261028`)를
  Cloudflare API로 배포해 `env.AI.run` 바인딩 경로로 측정했다.
  (`scripts/clairic-ab/probe-worker.js`, throwaway 헤더 키 인증, D1·시크릿 없음, 합성 메모만 처리.)
- 측정 후 **삭제 검증 완료**: DELETE 200 → GET 404 "This Worker does not exist on your account",
  workers.dev 접근 시 error 1042. `/tmp`의 probe 키도 삭제했다.
- `wrangler`는 이 VM에서 미인증 상태라 scratch 배포는 API 직접 호출로만 했다.
- 지연은 **Worker 내부 `env.AI.run` 실측값**을 1차로 쓴다.
  클라이언트 왕복(VM→probe→VM) 평균은 Clairic 1,469ms로 더 큰데, 이는 VM 프록시 RTT +
  전송 재시도 대기(아래)가 섞인 값이라 모델 지연 비교에는 쓰지 않는다.
- 전송 재시도 16회 (Clairic 7 / GLM 4 / llama 5) — 긴 호출에서 연결이 끊겨 3초 대기 후 재시도한 횟수.
  재시도는 서버에서 모델을 두 번 돌릴 수 있어 뉴런 소모를 소폭 부풀린다 (측정 오차로 기록).
- 측정 중 장애 2건 (모두 복구, 데이터 손실 없음):
  1. 체크포인트 쓰기 중 `PermissionError` 1회 — `--resume`으로 이어서 측정 완료.
  2. exec 세션 종료 시 stdout 파이프가 닫혀 `BrokenPipeError`로 러너 사망 1회 —
     원인은 print가 try 안에 있었던 것. `run_ab.py`를 수정해 print를 try 밖으로 뺐다.
     결과 파일의 `errors` 1건(EN-06 clairic Broken pipe)은 이 아티팩트이며, 해당 호출 기록은
     정상 존재한다 (90/90 유일 기록, 중복·누락 없음).

### 2.4 비용 계산

- 뉴런: Clairic은 가격표 환산율(9,091/M 입력)로 토큰에서 계산 (Clairic usage에 뉴런 필드가 없음).
  LLM 2개는 Workers AI가 usage에 반환한 **live `neurons` 값**을 그대로 썼다
  (가격표 계산과 정확히 일치함을 1건 대조로 확인: 166 입력 + 400 출력 → 15.473 뉴런).
- USD: 가격표 단가로 계산. 무료 10,000 뉴런/일 안에서는 $0이다.

## 4. 오차 분석 — 숫자가 말하는 것

### 4.1 `task` 필드는 정의가 모호하다 (전 arm 공통, 실패의 40% 이상)

- Clairic task 실패 15건 중 12건, GLM 20건 중 다수, llama 17건 중 다수가 **"정답 null인데 모델이 활동을 task로 뽑음"**이다.
  예: "치과 예약을 했다"(완료된 일)를 `치과 예약`으로, "저녁 약속이 있다"를 task로, "take a yoga class"를 task로.
- GT 정의는 "아직 해야 할 일"인데, 모델은 "메모 속 활동"으로 읽는다.
  **필드 정의의 문제지 모델의 문제가 아니다.** 평가셋 v2에서는 task를
  "아직 안 한 일"로 지침에 명시하거나, 완료된 행동이 있는 메모를 분리해야 한다.
- task를 빼면 세 arm이 87~88%로 동점이 된다 (§3.1). 즉 task가 순위를 가르고 있다.

### 4.2 상대 날짜가 정확도를 가른다 — Clairic이 가장 낫다

| 날짜 종류 | Clairic | LLM (GLM) | LLM-fast (llama) |
|---|---|---|---|
| 절대 날짜 (11건: "11월 5일", "November 10th" 등) | **100%** | **100%** | **100%** |
| 상대 날짜 (19건: 내일·모레·금요일·tomorrow·Friday 등) | **68.4% (13/19)** | 63.2% (12/19) | 21.1% (4/19) |

- llama는 상대 날짜를 거의 못 푼다 — 모르면 기준 날짜(10-28) 그대로를 답하거나 하루 어긋난다
  ("Friday"→10-29, "Saturday"→10-30, "Next Monday"→11-01).
- Clairic·GLM도 **"모레"를 전부 틀렸다** (KO-02: 모레→10-29, conf 0.9999 — 고신뢰 오답).
  "모레"는 세 arm 모두의 공통 약점이다.
- Clairic의 상대 날짜 실패 6건 중 3건은 오답이 아니라 **null 반환**(내일·어제·tomorrow에 p_null 0.56~0.999)이다.
  상대 날짜를 "날짜가 아님"으로 보는 경향이 있다.

### 4.3 Clairic의 일반명사 장소 null 반환 — 체계적 패턴 (8건)

Clairic이 장소를 null로 돌린 경우: 백화점, 회사 근처 식당, 도서관, department store,
cafe near the office, library, restaurant in front of the office, 회사 앞 식당.
전부 **일반명사 장소**다. 고유명사 장소(강남역 스터디카페, 서울월드컵경기장, Han River Park)는 잘 뽑는다.
p_null이 0.85~0.99로 높아서 임계값 게이트도 못 잡는다 (§6). place 필드 지침에
"도서관·백화점 같은 일반명사 장소도 포함"을 명시하면 개선될 가능성이 크다 — 미검증 가설이다.

### 4.4 GLM arm의 무응답 — 10% catastrophic failure

- GLM은 **3/30건(KO-07, KO-15, EN-12)에서 빈 답**을 냈다. 전부 completion_tokens가 정확히 2,000(상한)에 도달했고
  지연은 62초·44초·31초였다. 추론이 답을 낼 토큰을 남기지 않았다.
- 이 3건이 GLM 실패 40건 중 17건을 차지한다. 빼면 GLM 정확도는 **85.8% (139/162)** 로 세 arm 중 가장 높다.
  즉 GLM의 문제는 정확도가 아니라 **10% 확률로 아예 답이 없다는 것**이다.
  메모 저장 시 추출이 10% 확률로 통째로 실패하면 운영에서 바로 체감된다.
- llama는 무응답 0건, Clairic도 무응답 0건이다.

### 4.5 나머지 주목할 실패

- **금액은 Clairic·llama 100%.** GLM만 90% (무응답 3건 중 금액 필드가 포함돼서다).
- **시간 오탐**: "점심"→12:00 (Clairic conf 0.862, llama도 동일), "저녁"→20:00 (Clairic conf 0.328 — 낮음),
  "evening"→18:00 (llama). "점심/저녁" 같은 모호한 시간 표현은 모델이 시계를 추측한다.
- **고신뢰 오답은 2건뿐**: KO-02 모레 날짜(conf 0.9999), EN-02 place "Hongdae"(conf 0.9994, 정답은 "Italian restaurant in Hongdae").
  둘 다 스팬이 짧게 잘린 경우다.

## 5. 비용 구조 — 스키마 토큰이 본문보다 비싸다

Clairic 호출 1건의 입력 토큰 구성 (평균 794):

| 구성 | 토큰 | 비중 |
|---|---|---|
| 스키마 토큰 (필드 6개 정의) | 592 | 74.6% |
| state 토큰 (메모 본문 + 기준 날짜) | ~50 | 6.3% |
| 나머지 오버헤드 (passes 4회 분할 등) | ~150 | 19% |

- **짧은 메모에서는 필드 정의가 본문의 12배 토큰을 쓴다.** 필드를 줄이거나 지침을 짧게 하면
  Clairic 비용이 거의 비례해 줄어든다. 반대로 필드를 12개로 늘려도 스키마가 2배가 될 뿐 본문은 그대로라,
  **필드가 많을수록 Clairic의 상대적 이점이 커진다** (블로그의 "30개 필드가 3개와 비슷" 주장과 같은 방향).
- passes는 전 호출 4회로 일정했다 — 6개 필드가 4개 패스로 나뉜다. 패스 수가 비용에 어떻게 반영되는지는
  input_tokens에 이미 포함돼 있다 (808 토큰/KO-01 = state 54 + schema 592 + 오버헤드 162).
- GLM의 비용은 출력(추론) 토큰이 지배한다: 입력 153 vs 출력 1,055 토큰/호출.
  뉴런의 97%가 출력 쪽이다. thinking 모델을 추출에 쓰면 추론세가 붙는다.

## 6. confidence 임계값 설계

### 6.1 측정 기반

Clairic의 confidence·p_null 분포 (180판정):

| 신호 | 정답 평균 | 오답 평균 |
|---|---|---|
| confidence (non-null 예측 135건) | 0.954 | 0.618 |
| p_null (null 예측 45건) | 0.971 (정답 null) | 0.856 (오답 null) |

신호는 있다 (평균이 0.95 vs 0.62로 갈린다). 그러나 **고신뢰 오답이 존재**하고 (conf ≥0.99 오답 2건),
정답인데 conf <0.5인 경우도 4건이라, 임계값 하나로 오답을 깔끔히 걸러낼 수는 없다.

### 6.2 임계값 스윕 — 값 예측 자동 승인 (confidence ≥ t)

| t | 자동 승인 | 정밀도 | 재현율 (존재 필드 기준) | 재검토 비율 |
|---|---|---|---|---|
| 0.5 | 114건 (85.1%) | 96.5% | 82.1% | 14.9% |
| 0.8 | 107건 (79.9%) | 97.2% | 77.6% | 20.1% |
| 0.9 | 105건 (78.4%) | 98.1% | 76.9% | 21.6% |
| 0.95 | 100건 (74.6%) | 98.0% | 73.1% | 25.4% |
| 0.99 | 91건 (67.9%) | 97.8% | 66.4% | 32.1% |
| 0.999 | 76건 (56.7%) | 97.4% | 55.2% | 43.3% |

**정밀도는 t=0.5→0.9에서 96.5%→98.1%로 1.6pp 오르는 데 그치고, 재현율은 5.2pp 떨어진다.**
t를 0.99까지 올려도 정밀도는 97.8%로 오히려 소폭 내려간다 (표본이 작아진다).
즉 confidence 단독 임계값은 **정밀도를 사는 대신 재현율을 파는 거래**이며, 이득이 작다.

### 6.3 null 예측 자동 승인 (p_null ≥ t)

| t | 자동 승인 | null 정밀도 | null 재현율 |
|---|---|---|---|
| 0.5 | 32건 | 100% | 69.6% |
| 0.8 | 30건 | 100% | 65.2% |
| 0.9 | 30건 | 100% | 65.2% |
| 0.95 | 28건 | 100% | 60.9% |
| 0.99 | 27건 | 100% | 58.7% |

p_null ≥0.5로 null을 받아들이면 틀린 적이 없다(32/32). 다만 정답 null의 30%는 p_null이 낮아 재검토로 간다.

### 6.4 권장 결합 규칙 (측정값 기준)

**규칙 A — 값은 `confidence ≥ 0.9 AND p_null ≤ 0.1`, null은 `p_null ≥ 0.9`, 나머지는 재검토:**

| 규칙 | 자동 처리 | 자동 정밀도 | 재검토 | 재검토가 잡은 오답 |
|---|---|---|---|---|
| A (권장) | 140/180 (77.8%) | 92.9% | 40건 (22.2%) | 오답 34건 중 24건 |
| B (conf≥0.8 & p_null≤0.2; null p_null≥0.8) | 145/180 (80.6%) | 91.7% | 35건 | — |
| C (conf≥0.95; null p_null≥0.95) | 134/180 (74.4%) | 94.0% | 46건 | — |
| D (conf≥0.5만) | 167/180 (92.8%) | 85.0% | 13건 | — |

- 규칙 A가 균형점이다: 자동 정밀도 92.9%에 재검토 22%. 규칙 C는 정밀도 94.0%지만 재검토가 26%로 늘어난다.
- **규칙 A로도 자동 승인된 오답이 10건 남는다.** 그중 6건이 일반명사 장소 null (§4.3) —
  p_null이 높아서 null 게이트를 통과한다. **임계값만으로는 이 실패 모드를 못 잡는다.**
  장소 필드 지침 개선(§4.3) 또는 "장소는 null이어도 재검토" 같은 필드별 예외가 필요하다.
- 나머지 자동 승인 오답: 모레 날짜(고신뢰), "Hongdae" 짧은 스팬, 상대 날짜 null 2건.
- 운영 적용 시 재검토 22%는 "메모 저장 시 5개 필드 중 1개꼴로 사람 확인"이라는 뜻이다.
  자동 저장이 목표면 재검토율을 낮춰야 하고, 그 경우 정밀도가 90% 아래로 떨어진다 (§6.2 D 규칙 85.0%).
  **정밀도 95%+ 자동 저장은 이 데이터로는 안 나온다** — 필드 정의·지침 개선이 선행돼야 한다.

### 6.5 승인 게이트 연동안 (설계만 — 미구현)

- Clairic 추출 결과를 `captureFacts`의 사실로 쓰기 전, 규칙 A로 자동/재검토를 나눈다.
- 자동: 사실 저장 + 그래프 연결 (현행 결정적 경로와 동일).
- 재검토: 승인 게이트(기존 위험 기반 승인 설계)로 넘긴다 — 낮은 confidence·높은 p_null·중간값은
  사람 확인 없이 저장하지 않는다. 특히 **날짜·금액 필드는 오답 비용이 커서** 재검토 시 원문 스팬을 함께 보여준다.
- `p_null`이 높은 null은 "없음"으로 저장하지 말고 **필드 부재**로 처리한다 (없는 사실을 만드는 것보다 낫다).

## 7. GO / NO-GO 판단 근거

GO라고 단정하지 않는다. 아래 수치로 판단한다.

### GO 쪽 근거

1. **지연**: 230ms로 메모리 저장 시 동기 호출이 가능한 수준이다. GLM(21초)은 동기 호출이 불가능하고,
   llama(3.2초)도 체감상 느리다. 03:00 수면 통합 같은 배치에서도 Clairic이 14배 빠르다.
2. **상대 날짜**: 세 arm 중 유일하게 68%를 넘긴다. 일정·메모 파싱의 핵심 약점을 가장 잘 메운다.
3. **금액 100% + 절대 날짜 100%**: 숫자·날짜 같은 "틀리면 안 되는" 필드가 강하다.
4. **출력 토큰 0**: 비용이 입력에만 비례해 예측 가능하다. 토큰당 단가는 llama보다 비싸지만(§5),
   필드 수가 늘면 스키마 분할 구조상 상대 이점이 커진다.
5. **무료 한도 내**: 하루 1,385메모까지 무료. 개인용 메모량으로는 사실상 $0이다.
6. **null 정밀도**: p_null ≥0.5인 null은 32/32 정답 — "없음"을 믿을 수 있다.

### NO-GO / 보류 쪽 근거

1. **정확도가 LLM과 동점이다.** task 제외 시 87~88%로 세 arm이 같다.
   정확도만으로는 Clairic으로 갈아탈 이유가 없다 — 이유는 지연·비용·신뢰성이지 정확도가 아니다.
2. **프리뷰 리스크 (공식)**: AS IS 약관, 오픈 웨이트 미공개, 체크포인트 변경 가능.
   운영의 메모리 추출을 프리뷰 모델 하나에 거는 것은 리스크다. **결정적 경로를 폴백으로 두지 않으면 안 된다.**
3. **일반명사 장소 null (8건) + 모레 오답 (고신뢰)**: 임계값으로 못 잡는 체계적 실패가 있다.
   장소 지침 개선 후 재측정이 필요하다.
4. **한국어 −6.6pp**: EN보다 낮다. 상대 날짜·task 정의가 원인이라 필드·평가셋 개선 후 재측정 필요.
5. **정밀도 95%+ 자동 저장은 안 된다.** 규칙 A로도 자동 정밀도 92.9%, 재검토 22%.
   "사람 확인 없이 저장"을 목표로 하면 이 수치는 부족하다.
6. **GLM이 정확도 자체는 더 높을 수 있다** (무응답 제외 시 85.8%). Clairic의 우위는 신뢰성·지연이지 정확도가 아니다.
7. **스키마 토큰 비용**: 짧은 메모·적은 필드에서는 llama-8b보다 뉴런이 2배 비싸다.
   필드가 6개 이하인 단순 추출에는 llama이 쌀 수 있다.

### 운영 도입 전제 조건 (이 중 하나라도 안 되면 NO-GO)

1. **결정적 경로 폴백 유지**: Clairic 실패·무응답·프리뷰 중단 시 `extractFacts`로 자동 폴백.
   Clairic을 유일한 추출 경로로 만들지 말 것.
2. **장소 지침 개선 + 재측정**: 일반명사 장소를 포함하도록 place 지침을 고치고, 같은 평가셋으로
   place 정확도·null률이 개선되는지 확인한다.
3. **task 필드 정의 확정**: "아직 해야 할 일"로 지침을 명시하고 평가셋 v2(완료된 행동 분리)로 재측정한다.
4. **규칙 A 게이트 구현**: 자동/재검토 분리 + 재검토는 승인 게이트로. 자동 저장만으로 도입하지 않는다.
5. **체크포인트 안정화 확인**: 프리뷰 종료 또는 체크포인트 고정 공지가 나올 때까지 운영 도입을 미룬다.
   그 전에는 격리 환경(일회용 스크래치 Worker·miniflare·단위 테스트)에서만 쓴다.
   최종 적용은 `deploy_full.py production` 직접 배포로 한다 (배포는 별도 결정, 이 작업에서 하지 않음).
   실무에 스테이징 환경은 없다.
6. **잠긴 메모 절대 제외**: Clairic 입력에 잠긴 메모·민감정보를 넣지 않는다 (기존 경계와 동일).
   긴 프롬프트 금지 (GLM-5.3 KV 캐시 사고 교훈 — 메모는 짧지만 원칙 유지).

## 10. 확인 못한 것 (정직한 기록)

- **Gemini 추출기와의 비교**: Gemini 키는 시크릿이라 측정하지 않았다.
  MyHub 비서의 실제 LLM(Gemini 3.5-flash-lite)이 이 평가셋에서 어떻게 나오는지는 미확인이다.
- **MyHub 자체 Worker에서의 `env.AI.run`**: probe Worker(격리 스크립트)에서만 확인했다.
  MyHub Worker에 Clairic 바인딩을 붙인 동작은 미확인이나, 바인딩 방식은 동일하다.
- **긴 메모·여러 날짜가 있는 메모**: 평가셋은 2~3문장·날짜 1개 위주다.
  긴 메모·복수 날짜·표 형태 메모에서의 동작은 미확인이다.
- **체크포인트 안정성**: 프리뷰라 다음 체크포인트에서 수치·동작이 바뀔 수 있다. 재측정 전에는 이 수치를 고정값으로 쓰지 말 것.
- **오픈 웨이트**: 미공개라 로컬 실행·가중치 검증은 불가하다.
- **Workers AI REST 401의 근본 원인**: 토큰 스코프 부재로 추정되나, 토큰의 스코프 목록을 직접 확인하지는 않았다.
  (스코프 확인용 엔드포인트가 없고, 토큰 재발급은 사용자 몫이라 더 파지 않았다.)
