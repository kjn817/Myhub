# MyHub 58차 기술 검토 요청 (GPT용)

## 1. 개요

- 일시: 2026-10-13 20:10 KST
- 이슈: 에코(keeper) 비서의 메모 도구(MEMO_*)가 동작하지 않음
- 심각도: P0 (에코의 핵심 기능인 메모 관리 불가)
- 상태: 원인 확정, 해결 방안 결정 필요

## 2. 문제 상세

### 2.1 증상

에코에게 메모 생성을 요청하면:
- **기대**: `[MEMO_CREATE]{"text": "내용"}[/MEMO_CREATE]` 마커 출력 → 백엔드가 파싱하여 실제 메모 생성
- **실제**: `MEMO_CREATE 제목='...' 내용='...'` 평문 출력 → 백엔드가 인식하지 못함 → 메모 미생성

동일한 문제가 메모 조회/수정/삭제 모두에서 발생. 메모 페이지 위젯과 메인 채팅 모두에서 재현됨.

### 2.2 테스트 결과

| 기능 | 결과 | 비고 |
|------|------|------|
| 메모 생성 | ❌ 실패 | 마커 형식 오류로 미생성 |
| 메모 검색 | ❌ 환각 | 가짜 내용 보고 |
| 메모 편집 | ❌ 환각 | "성공" 거짓 보고, 실제 변경 없음 |
| 메모 꾸미기 | ❌ 실패 | 채팅창에만 표시, 실제 미적용 |
| 메모 닫기 | ❌ 실패 | 열린 메모 인식 못함 |
| 잠금 보안 | ✅ 통과 | 잠긴 메모 열람/해제 거부 확인 |

### 2.3 근본 원인

에코가 사용하는 Llama 3.3 70B (Workers AI: `@cf/meta/llama-3.3-70b-instruct-fp8-fast`)가
텍스트 마커 형식을 정확히 따르지 않음.

## 3. 현재 아키텍처

### 3.1 마커 기반 도구 호출

**파일**: `src/services/ai.ts` (프롬프트 정의)

```
- 메모 작성: [MEMO_CREATE]{"text": "내용"}[/MEMO_CREATE]
- 메모 수정: [MEMO_UPDATE]{"id": 123, "text": "새 내용"}[/MEMO_UPDATE]
- 메모 삭제: [MEMO_DELETE]{"id": 123}[/MEMO_DELETE]
```

**파일**: `src/services/memo-tools.ts` (파서)

백엔드가 AI 응답 텍스트에서 정규식으로 마커를 추출하여 실행.

### 3.2 비서별 프로바이더 (2026-10-13 확정)

- 루미(concierge) → Gemini (`gemini-3.5-flash-lite`)
- 에코(keeper) → Workers AI (`@cf/meta/llama-3.3-70b-instruct-fp8-fast`)
- 노바(builder) → NVIDIA (`poolside/laguna-xs-2.1`)
- 캘리(scheduler) → Groq (`openai/gpt-oss-120b`)

Provider 간 폴백 없음 (providerPin으로 고정).

## 4. 해결 방안 후보

### 방안 1: 프롬프트 개선
- 마커 형식을 더 명확히 지시
- Few-shot 예제 추가
- **장점**: 코드 변경 최소, 빠른 적용
- **단점**: Llama의 지시 이행 능력이 근본적 한계일 수 있음

### 방안 2: 모델 교체
- 에코를 지시 이행이 더 정확한 모델로 변경
- 후보: Groq의 Llama 3.3 70B (같은 모델이지만 Groq 버전이 더 나을 수 있음), 또는 다른 모델
- **장점**: 모델 능력 문제면 확실한 해결
- **단점**: Workers AI를 사용해야 한다는 사용자 요구와 충돌. 프로바이더 고정 원칙 위배.

### 방안 3: Function Calling 도입
- 텍스트 마커 대신 정식 Function Calling API 사용
- **장점**: 구조적 해결, 환각 방지
- **단점**: 대규모 코드 변경, Workers AI의 Function Calling 지원 여부 확인 필요, 테스트 부담 큼
