# GPT 자문 요청: MyHub 아티팩트 → 모듈형 OS 첫단계 설계

## 현재 상태 (2026-10-14)

노바(kimi-k3) 아티팩트 E2E 전체 흐름 검증 완료:
- HTML 생성 → D1 초안 저장 → 격리 미리보기 → 게시 승인 → 홈 "노바의 공간"에서 실행
- 샌드박스 iframe (`allow-scripts`, `allow-same-origin` 없음)
- 초안/게시 상태 분리, 게시 버튼 승인 방식

DB 스키마:
```sql
artifacts(id, title, type, html_content, status, created_at, updated_at)
-- status: 'draft' | 'published'
```

## 사용자 비전: MyHub OS 첫단계

아티팩트를 일회성 HTML이 아니라 **버전 관리되는 앱 모듈**로 발전시키고 싶음:

1. **버전 관리**: 아티팩트에 버전 히스토리, 업데이트 가능해야 함
2. **에이전트화**: 내 앱에서 돌아가는 작은 에이전트/도구들
3. **커스터마이징**: GitHub의 핫한 프로젝트들(예: rea 같은 리버스엔지니어링 도구)을 참고해서 필요한 것들을 만들어내고, 입맛에 맞게 모듈 수정, 아이콘 변경
4. **MyHub OS**: 작은 유틸리티 모듈들을 하나씩 만들어서 OS처럼 조립하는 장기 비전 (2026-10-05부터)

## GPT에게 묻고 싶은 것

### Q1. 아티팩트 버전 관리 설계
현재 `artifacts` 테이블은 단일 버전만 저장함. 버전 히스토리를 어떻게 설계해야 하는가?
- 옵션 A: `artifact_versions(artifact_id, version, html_content, created_at)` 별도 테이블
- 옵션 B: `artifacts`에 `version`, `parent_version_id` 컬럼 추가
- 롤백, diff 표시, 자동 업데이트 알림까지 고려한 권장 구조는?

### Q2. 아티팩트 → 모듈 (앱) 승격 경로
단순 HTML 아티팩트가 "설치된 앱"이 되려면 무엇이 필요한가?
- 아이콘 (사용자가 변경 가능해야 함)
- 앱 메타데이터 (이름, 설명, 권한 요청)
- 홈화면 진입점 (위젯 vs 전체화면 앱)
- 업데이트 메커니즘 (노바에게 "이 앱을 이렇게 바꿔줘" → 새 버전)
- 권한 모델 (아티팩트가 접근할 수 있는 MyHub API 범위)

### Q3. 외부 프로젝트 참고 (rea 등)
GitHub에서 핫한 도구들을 아티팩트로 가져올 때:
- 현재 GitHub 가져오기는 README를 HTML로 저장하는 수준임
- 실제 동작하는 도구를 안전하게 포팅하려면 어떤 검증 단계가 필요한가?
- 라이선스 확인, 의존성 분석, 샌드박스 호환성 체크의 권장 프로세스는?

### Q4. MyHub OS 아키텍처 방향
장기적으로 작은 모듈들을 OS처럼 조립하려면:
- 모듈 간 통신 (postMessage? 공유 스토리지? 이벤트 버스?)
- 모듈 마켓플레이스/등록 구조
- 노바가 모듈을 생성·수정·배포하는 전체 라이프사이클
- 지금 당장 깔아야 할 기반 vs 나중에 추가해도 되는 것
