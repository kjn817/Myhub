# 샌드박스 격리 옵션 평가 (진짜 비서 3단계 i트랙, 2026-10-26)

MyHub는 Cloudflare Workers에서 동작한다. Workers 런타임은 V8 isolate 기반이라
컨테이너·VM 수준의 샌드박스가 없다. Suna는 Docker 샌드박스 + Change Request
리뷰로, OpenManus는 Docker 샌드박스에서 코드 실행으로 격리한다. MyHub 환경에서
무엇이 가능한지, 네 가지 옵션을 평가한다.

조사 기준일: 2026-10-26. 출처는 Cloudflare 공식 문서
(developers.cloudflare.com/sandbox/, /workers/platform/pricing/,
/containers/platform/pricing/)와 Cloudflare Dynamic Workers 소개 글이다.
가격·플랜 조건은 조사 시점 기준이며, 도입 전에 다시 확인할 것.

## 전제 — MyHub의 위험은 "임의 코드 실행"이 아니다

MyHub의 AI 도구는 타입이 정해진 D1 연산이다 (메모/일정/할 일/자동화 CRUD,
Gmail·캘린더 읽기/쓰기). 모델이 만드는 것은 마커 텍스트이지 실행 코드가
아니며, 실행 경로는 `src/modules/ai/routes.ts`의 파서 → 게이트 →
실행기(services/*-tools.ts)로 고정돼 있다. 즉 격리해야 할 것은
"모델이 낸 임의 코드"가 아니라 "모델이 낸 도구 호출이 사용자의 데이터를
바꾸는 것"이다. 이 전제가 옵션 선택을 가른다.

이미 있는 안전장치 (b트랙, 2026-10-26):
- 위험 기반 승인 게이트 — 읽기 무승인, 쓰기 기본 승인, 삭제·외부 발송 반드시 승인
- 채팅 승인/거부/세션 허용 흐름 + 10분 만료 + 범위(도구+대상) 단위 승인
- 잠금 정책 — 잠긴 메모는 모든 외부 AI 전송 경로에서 제외, AI 잠금/해제 불가
- 도구 권한 경계 — 비서별 허용 도구 목록, 실행 시점 재검사, 인자 시크릿 마스킹

## 관련 기술 메모

- **Cloudflare Sandbox SDK 1.0** (2026-09-30 전후): 각 샌드박스 컨테이너를
  애플리케이션 자체 Durable Object가 `this.ctx.container`로 직접 제어한다.
  0.x의 standalone Sandbox/Container 클래스는 유지보수 모드. 도입한다면
  1.0 계열로 할 것. 이미지 `cloudflare/debian-trixie` 등, `enableInternet:
  false`로 외부망 차단 가능, R2 마운트로 파일시스템 지속 가능.
- **Dynamic Workers (workers loader 바인딩)**: 부모 Worker가 코드 문자열에서
  새 Worker를 런타임에 생성한다. `globalOutbound: null`로 네트워크 차단,
  바인딩 선택 노출로 D1/KV 접근 통제. 컨테이너가 아니라 V8 isolate 수준
  격리라 가볍고 빠르다. AI 생성 JS 스니펫 실행 같은 경량 코드 실행에 적합.
  단, MyHub의 현재 도구(타입 고정 D1 연산)에는 필요 없는 primitive다.
  스튜디오에서 사용자 정의 변환 스크립트 같은 것을 실행하게 될 때 재평가.
- **Suna / OpenManus 참고**: 둘 다 Docker 샌드박스에서 "에이전트가 만든
  코드"를 실행한다. MyHub에는 그에 해당하는 실행 표면이 아직 없다 —
  그래서 이들의 격리 방식을 그대로 가져오는 것은 과잉이다.

## 선택

**지금 채택: ③ dry-run + 미리보기 + 명시 승인** (이번 트랙에서 구현).

이유:
1. MyHub의 실제 위험은 임의 코드가 아니라 "확인 없는 데이터 변경"이다.
   미리보기 + b트랙 승인 게이트가 그 위험을 직접 겨냥한다.
2. 비용 0원, 카드·유료 플랜 전환 없음 — 사용자 원칙과 충돌하지 않는다.
3. 구현이 작고 되돌릴 수 있다. 감사 로그까지 갖추면 "무엇을·언제·누가
   승인했는지"가 남는다.

**보류 (문서 기록만, 도입하지 않음): ① Cloudflare Sandbox.**
Workers Paid 플랜($5/월) + Containers 사용량 과금이 필요해 사용자 원칙과
충돌하고, 지금 MyHub에는 격리할 임의 코드 실행 표면이 없다. 스튜디오에서
AI 생성 코드를 직접 실행하는 기능이 생기면 그때 재평가한다.

**다음 단계로 설계만 남김: ② 별도 격리 Worker.**
③이 자리를 잡은 뒤, 도구 실행기를 별도 Worker로 분리하는 설계를 검토한다.
전제 조건: 격리 Worker는 D1 쓰기 바인딩을 갖지 않고, 실행 요청을 받아
검증된 결과만 돌려주며, 최종 적용은 주 Worker가 승인 확인 후 수행한다.
이 전제가 깨지면 격리가 아니라 복잡성만 늘어난다. 구현은 사용자 결정 후.

**④는 ③에 흡수된다.** 게이트 강화만으로는 "무엇이 바뀌는지"를 보여주지
못하므로, ③의 미리보기가 ④의 한계를 메운다.

## 이번 트랙 구현 범위 (③)

1. `src/services/sandbox.ts` 신규 — 위험한 도구 실행 전 dry-run 미리보기
   (읽기 전용 조회로 "무엇이 바뀌는지" 계산, 잠긴 메모 내용은 절대 비노출),
   미리보기 문안 포맷, 실행 감사 로그 저장소.
2. `migrations/0055_tool_execution_audit.sql` 신규 — 감사 로그 테이블
   (`tool_execution_audit`: preview_shown / executed / denied / expired /
   blocked).
3. 승인 게이트 연결 (`src/modules/ai/routes.ts`) — 승인 요청을 만들 때
   dry-run 미리보기를 문안에 포함하고 감사 로그에 남긴다. 파괴적 실행은
   명시 승인 없이는 적용하지 않는다 (b트랙 게이트 그대로 — dry-run은
   게이트를 우회하지 않고, 미리보기 실패 시에도 실행하지 않는다).
4. 승인 응답 처리 — 승인 후 재실행 / 거부 / 만료 결과를 감사 로그에 남긴다.
5. 테스트 — 미리보기·승인 후 적용·감사 기록의 단위·통합 테스트
   (`tests/sandbox.test.ts`), FakeD1 확장.

## NOT TESTED / 결정 필요

- Cloudflare Sandbox 실제 동작: 유료 플랜이 필요해 테스트하지 않음
  (문서 조사만 수행). 도입 결정 시 스테이징에서 SDK 1.0 동작 검증 필요.
- 별도 격리 Worker: 설계안만 기록, 구현·테스트하지 않음.
- dry-run과 실제 실행 사이의 경합(미리보기 후 대상 변경): 미리보기는
  승인 시점의 스냅샷이며, 실행 직전 재검증은 하지 않는다. 실행기가
  대상 부재·잠금 상태를 실행 시점에 다시 검사하는 것으로 갈음한다
  (예: `executeMemoDelete`는 잠긴 메모 삭제를 실행 시점에 차단).
