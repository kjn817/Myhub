# 실시간 음성 파이프라인 설계 (2단계)

> 조사 + 설계 문서. **코드 변경 없음.** 근거는 `docs/github-apply-research-20261026.md` 2-6절(Pipecat / LiveKit)
> 및 3-5절(음성 심화 후보)과 현행 구현(`src/services/voice.ts`, `src/modules/voice/routes.ts`,
> `docs/voice-interface.md`)이다. 수치·라이선스는 조사 문서 기준일(2026-10-26) 값이며, 이 문서에서
> 새로 실측한 것은 없다. 작성: 2026-10-26.

## 0. 결론 먼저

- 실시간 음성의 핵심은 STT→LLM→TTS 연결이 아니라 **VAD(음성 감지)·인터럽션(말 끊기)·스트리밍·턴테이킹**이다.
- Pipecat / LiveKit은 둘 다 **Python 중심 서버 프레임워크**라 Workers에 통째로 들어가지 않는다.
  가져올 것은 **파이프라인 상태머신 패턴**뿐이다.
- LiveKit `agents-js`(TS 서버)는 ★951 대비 이슈 502건으로 성숙도가 낮아 **서버 도입 보류, 패턴만 참고**한다.
- TTS는 **MeloTTS 유지**. fish-speech / Moshi / faster-whisper / Coqui TTS는 지켜보기.
- 2단계(스트리밍·인터럽션)는 1단계 실기기 검증이 끝난 뒤에, 전제 조건(아래 5절)을 충족하는 순서로 간다.

## 1. 현행 1단계 — 단발 전사 + 합성 (구현됨, 라이브 미검증)

커밋 `cc0c60a`(진짜 비서 3단계 h트랙). 동작은 요청·응답 단발이다.

### 1.1 현재 흐름

```
브라우저 MediaRecorder 녹음 (사용자 탭으로 시작, 최대 60초)
  → POST /api/voice/transcribe (multipart, 오디오 파일 통째로 업로드)
  → Whisper 전사 (전체 파일 1회 호출)
  → 전사 텍스트를 /api/ai/chat 에 텍스트 입력과 동일하게 전달
  → 비서 응답 텍스트 전체를 받음 (현행 /api/ai/chat 은 SSE 스트리밍 없음 — JSON 요청·응답)
  → POST /api/voice/synthesize (응답 텍스트 전체)
  → MeloTTS 오디오 전체를 받아 <audio> 로 재생
```

- **스트리밍 없음**: 녹음이 끝날 때까지 전사가 시작되지 않고, 응답이 완성될 때까지 합성이 시작되지 않으며,
  합성이 끝날 때까지 재생이 시작되지 않는다. 지연은 각 단계 시간의 합이다.
- **VAD 없음**: 녹음 시작·종료는 사용자가 버튼으로 직접 한다. 말 끝 자동 감지 없음.
- **인터럽션 없음**: 재생 중 사용자가 말해도 재생이 멈추지 않고, 비서 응답 생성도 중단되지 않는다.
- **부분 전사 없음**: Whisper 호출은 파일 단위 1회.

### 1.2 현행 상수·한도 (코드 기준, `src/services/voice.ts`)

| 항목 | 값 |
| --- | --- |
| STT | `@cf/openai/whisper-large-v3-turbo`, 46.63 neurons/오디오 분 |
| TTS | `@cf/myshell-ai/melotts` (한국어 `kr` 지원), 18.63 neurons/오디오 분 |
| 무료 티어 | 계정당 **10,000 neurons/일 공유** (00:00 UTC 리셋, 초과 시 Free 플랜은 실패) |
| 녹음 상한 | 60초 · 2MB (초과 413) |
| TTS 입력 | API 5,000자 상한, 모델에는 1,000자로 잘라 전달 |
| 일일 상한 | 기본 100회(STT+TTS 합산, KV 카운터). `ai_settings`의 `voice.daily_limit` > 환경변수 `VOICE_DAILY_LIMIT` > 기본값 순 |
| 왕복 비용 | 60초 음성 왕복(STT 60초 + TTS 약 30초 분량) ≈ 56 neurons. 100회 ≈ 5,600 neurons |
| 오디오 저장 | 없음 (메모리에만 두고 호출 후 버림). 전사 텍스트는 일반 텍스트 입력과 동일 취급, 잠긴 메모에 닿지 않음 |

### 1.3 현행 iOS PWA 제약 (실기기 미검증 — NOT TESTED)

- MediaRecorder는 iOS Safari 14.5+ / PWA(standalone)에서 동작하나 mimeType은 `audio/mp4`(AAC)만 지원.
  `audio/webm`을 강제하면 생성 자체가 실패하므로 `public/js/voice.js`는 mp4 → webm/opus → 기본값 순으로 폴백한다.
- 녹음 시작과 오디오 재생은 반드시 **사용자 제스처(버튼 탭)** 안에서만 가능하다. 자동 재생·자동 녹음 없음.
- 무음 스위치가 켜져 있으면 `<audio>` 재생이 들리지 않을 수 있다 (기기 설정, 코드로 우회 불가).
- **1단계 실기기 종단 테스트(녹음 mp4 → 전사 → 재생) 자체가 아직 없다.** 2단계로 가기 전에 이 검증이 먼저다.

### 1.4 이미 제외된 선택지

- 실시간 스트리밍 STT(`@cf/deepgram/nova-3` WebSocket, 836.36 neurons/분)는 **비용 때문에 제외**
  (`docs/voice-interface.md`). Whisper 46.63 neurons/분의 약 18배다. 2단계에서 스트리밍 STT를 다시
  검토한다면 이 단가를 먼저 다시 계산해야 한다.

## 2. Pipecat / LiveKit 파이프라인 상태머신 패턴

근거: 조사 문서 2-6절. Pipecat(`pipecat-ai/pipecat`) ★16,816 · BSD-2-Clause · 이슈 439 ·
`tests/` + CI 존재 · Daily 유지. LiveKit Agents(`livekit/agents`) ★14,935 · Apache-2.0 · 이슈 806.
둘 다 실시간 음성 에이전트 프레임워크이며, 이 패턴의 사실상 표준이다.

**도입 방식: 서버 프레임워크를 설치하지 않는다.** 둘 다 Python 중심이라 Workers에 맞지 않는다.
이 절은 MyHub가 TypeScript/Workers로 **직접 구현할 때 따라야 할 상태머신**을 정리한 것이다.
프레임워크 내부 구현을 그대로 옮긴 것이 아니라, 조사 문서가 지목한 패턴
(VAD → 부분 전사 → LLM 스트리밍 → TTS 청크 재생 → 개입 시 중단·컨텍스트 절단)을 MyHub 환경에 맞게 푼 것이다.

### 2.1 상태머신

```
                    ┌────────────────────────────────────────────────────┐
                    │                    LISTENING                       │
                    │  마이크 입력 → VAD → 음성 구간만 STT로            │
                    └──────┬───────────────────────────────▲───────────┘
                           │ VAD: 발화 종료 감지            │ 인터럽션 처리 완료
                           ▼                                │ (아래 2.5)
                    ┌──────────────┐
                    │ TRANSCRIBING │  부분 전사 누적 (확정 구간만 LLM으로)
                    └──────┬───────┘
                           │ 발화 확정 (최종 전사)
                           ▼
                    ┌──────────────┐
                    │  THINKING /  │  LLM 스트리밍 시작
                    │  GENERATING  │  첫 토큰 → 문장 경계 단위로 TTS 큐에 투입
                    └──────┬───────┘
                           │ 문장 단위 TTS 청크 완성
                           ▼
                    ┌──────────────┐
                    │   SPEAKING   │  TTS 청크 순차 재생
                    └──────┬───────┘
                           │ 재생 완료
                           └──────────────→ LISTENING
```

상태는 한 번에 하나이며, 전이는 **이벤트**로만 일어난다: `vad_start`, `vad_end`,
`transcript_final`, `llm_first_token`, `tts_chunk_ready`, `tts_done`, `user_barge_in`.
타이머·추측으로 상태를 바꾸지 않는다.

### 2.2 단계별 설계

#### (1) VAD — 음성 구간 검출 (LISTENING)

- **역할**: 마이크 스트림에서 "지금 사람이 말하고 있다"는 구간만 잘라낸다. 무음은 STT로 보내지 않는다.
- **MyHub 적용 방식**: Workers AI 바인딩에는 VAD 전용 모델이 없다. 현행에 쓰는 모델은 Whisper/MeloTTS뿐이다.
  따라서 VAD는 **브라우저 측**에서 수행하는 것이 현실적이다. 후보는 두 갈래이며, 이 문서 시점에서는 미결정이다.
  - (a) Web Audio API 기반 에너지·영점 교차율 임계값 — 의존성 없음, 정확도는 낮고 환경 소음에 약하다.
  - (b) wasm으로 도는 경량 VAD 모델 — 정확도는 높으나 번들·로딩·iOS PWA 동작을 별도로 검증해야 한다.
- **종료 판정**: 무음이 일정 시간(예: 500ms~1s, 값은 실측으로 정할 것) 지속되면 발화 종료로 본다.
  너무 짧으면 말 중간에 끊기고, 너무 길면 응답이 늦어진다. 이 값은 튜닝 상수이며, 코드에 하드코딩하지 말고
  설정으로 빼는 것을 전제로 한다.
- **Workers 제약**: VAD를 서버(Worker)에서 하려면 오디오를 계속 보내야 하는데, 일반 Worker 요청은
  단발이다. 지속 오디오 업로드는 WebSocket(Durable Objects)이나 청크 업로드가 필요해 2단계 전제 조건(5절)과 묶인다.

#### (2) 부분 전사 — 확정 구간만 LLM으로 (TRANSCRIBING)

- **역할**: 발화가 끝나기 전에도 중간 전사(부분 결과)를 받아 UI에 표시하고, 발화가 확정되면 최종 전사만
  LLM에 넘긴다. 부분 결과를 LLM에 그대로 넘기지 않는다 — 부분 전사는 바뀌기 때문이다.
- **MyHub 적용 방식**: 현행 Whisper 바인딩은 **파일 단위 배치 호출**이라 부분 전사를 직접 주지 않는다.
  2단계에서 부분 전사를 흉내 내려면 발화 중 오디오를 짧은 청크(예: 2~3초)로 나눠 Whisper를 반복 호출하는
  방식이 있으나, 이 경우 비용과 정확도에서 손해가 생긴다.
  - **비용**: 청크마다 전체 오디오 분 단가가 붙는다. 겹치는 구간이 있으면 같은 음성을 두 번 과금한다.
    46.63 neurons/분을 기준으로, 1분 대화를 청크 20번으로 나누면 STT만 수백 neurons가 된다.
    무료 티어 10,000 neurons/일 공유 한도 안에서 2단계의 분당 비용을 먼저 계산해야 한다.
  - **정확도**: 짧은 청크는 문맥이 잘려 전사 품질이 떨어진다. 청크 경계에서 단어가 잘리는 문제도 있다.
  - **결론**: 2단계 1차 목표는 "부분 전사"가 아니라 **(1) VAD 자동 종료 + (5) 인터럽션**으로 잡는 것이
    비용·복잡도 면에서 맞다. 부분 전사는 그 다음 단계에서 스트리밍 STT 단가(Deepgram nova-3 등)를
    다시 계산한 뒤에 결정한다.

#### (3) LLM 스트리밍 — 첫 토큰부터 TTS로 (THINKING / GENERATING)

- **역할**: LLM 응답이 완성될 때까지 기다리지 않고, 토큰이 나오는 대로 문장 경계에서 잘라 TTS 큐에 넣는다.
  첫 문장이 나오면 바로 합성을 시작해 "생각하는 시간"을 체감 지연에서 빼는 것이 목적이다.
- **MyHub 적용 방식 — 전제 조건**: 현행 `/api/ai/chat`은 **SSE 스트리밍이 없는 JSON 요청·응답**이다.
  따라서 LLM 스트리밍은 2단계의 별도 선행 작업이다. 텍스트 채팅의 스트리밍이 먼저 동작해야 음성도 스트리밍할 수 있다.
- **문장 경계 절단**: 토큰 스트림을 `.` `!` `?` `。` 등 종결 부호 기준으로 자른다. 단, 약어·숫자·URL의
  마침표는 오절단되므로, 현행 `stripForTts`의 문장 절단 로직을 재사용·확장하는 방향으로 설계한다.
  TTS 입력 상한(모델 1,000자)은 문장 단위에서는 보통 문제가 되지 않으나, 긴 문장은 추가로 자르는 규칙이 필요하다.
- **스트리밍 중 취소**: 사용자가 개입하면 LLM 스트림도 중단해야 한다. 중단 신호는 (5) 인터럽션과 같은 경로로 처리한다.

#### (4) TTS 청크 재생 — 문장 단위 순차 재생 (SPEAKING)

- **역할**: 응답 전체를 한 번에 합성해 재생하지 않고, 문장 단위 청크를 합성되는 순서대로 재생한다.
  앞 문장이 재생되는 동안 뒷문장을 합성해 대기 시간을 숨긴다.
- **MyHub 적용 방식**: 현행 MeloTTS 호출은 **텍스트 전체 → 오디오 전체**의 배치 호출이다.
  문장 단위로 나누어 호출하면 청크마다 별도 호출이 되므로, 호출 횟수가 늘고 일일 100회 상한(KV 카운터)에
  문장 수가 그대로 반영된다. 상한 정책은 "요청 수"가 아니라 "문장 청크 수" 기준으로 다시 정의해야 한다.
  - **청크 경계**: 문장 경계에서만 자른다. 문장 중간에 자르면 억양이 깨진다.
  - **재생 큐**: `AudioContext`/`HTMLAudioElement` 큐로 청크를 순서대로 재생한다. 다음 청크가 아직 합성 중이면
    앞 청크 재생이 끝난 뒤 짧게 기다린다. iOS PWA에서는 재생이 사용자 제스처 안에서만 허용되므로,
    **첫 재생을 시작하는 제스처 이후의 연속 재생이 iOS에서 끊기지 않는지 실기기 검증이 필수**다.
    (자동 재생 제한은 1단계에서도 미검증 항목이다.)
  - **비용**: MeloTTS는 18.63 neurons/오디오 분으로, 문장으로 나눠도 총 오디오 분량은 같아 뉴런 총량은
    크게 달라지지 않는다. 단, 호출 횟수 상한과 별개로, 청크마다 오버헤드(합성 시작 지연)가 생긴다.

#### (5) 인터럽션 — 말 끊기 + 컨텍스트 절단 (전 상태에서 LISTENING으로)

- **역할**: 비서가 말하는 도중 사용자가 말을 시작하면, 즉시 재생을 멈추고 LLM 생성을 중단하며,
  이미 말한 부분까지만 컨텍스트에 남긴다. 이것이 실시간 대화의 핵심이다.
- **전환 규칙**:
  1. `SPEAKING` 상태에서 VAD가 사용자 발화를 감지하면 즉시 `user_barge_in` 이벤트 발생.
  2. **재생 중단**: 현재 재생 중인 오디오를 즉시 정지하고 재생 큐를 비운다. 큐에 남아 있던 TTS 청크는 버린다.
  3. **생성 중단**: 진행 중인 LLM 스트림을 중단한다 (스트리밍이 전제 조건인 이유).
  4. **컨텍스트 절단**: 비서 응답은 **실제로 재생된 부분까지만** 대화 기록에 남긴다. 재생되지 않은 뒷부분을
     기록에 남기면, 사용자는 듣지도 않은 말을 비서가 한 것으로 기억하게 된다. 절단 단위는 문장 청크이며,
     부분적으로 재생된 문장은 재생된 부분까지만 남기거나, 문장 단위로 버리는 규칙을 정해야 한다
     (이 문서 시점에서는 미결정 — 구현 시 결정).
  5. `LISTENING`으로 돌아가 사용자 발화를 받는다. 단, 사용자가 비서를 끊은 것이 아니라 기침·소음 등
     오탐이면 대화가 끊긴다. VAD 임계값과 최소 발화 길이(예: 300ms 이상)로 오탐을 줄이는 설계가 필요하다.
- **MyHub 적용 시 주의**: 현행 1단계에는 인터럽션 경로가 전혀 없다. 2단계에서 인터럽션만 따로 구현하려면
  (3) LLM 스트리밍과 (4) 청크 재생이 먼저 있어야 한다. 순서가 뒤바뀌면 인터럽션은 동작하지 않는다.
- **에코(자기 목소리) 문제**: 스피커로 나오는 비서 음성이 마이크에 다시 들어가 VAD가 사용자 발화로 오인할 수 있다.
  브라우저 `echoCancellation: true`로 어느 정도 줄일 수 있으나 완전하지 않다. 재생 중에는 VAD 임계값을
  높이거나, 재생 중인 오디오를 참조 신호로 빼는 처리가 필요할 수 있다 — 이 부분은 실측 없이 단정하지 않으며,
  2단계 테스트 항목에 넣는다.

### 2.3 Workers 환경 제약 — 이 설계의 경계

| 제약 | 내용 | 설계에 미치는 영향 |
| --- | --- | --- |
| Python 프레임워크 불가 | Pipecat / LiveKit 서버는 Python 중심. Workers에는 Python 런타임이 없다 | 서버 통째 도입 금지. 상태머신 패턴만 TS로 직접 구현 |
| 단발 요청 구조 | 일반 Worker 요청은 요청·응답 1회. 지속 연결이 아니다 | 실시간 양방향 채널이 필요하면 Durable Objects WebSocket이 공식 경로다. 단, Durable Objects는 이 문서 시점의 MyHub 아키텍처에 없으므로 2단계 전제 조건으로 별도 검토가 필요하다 |
| 30초 edge 제한 (추정) | `/api/ai/websearch`가 체인 순차 실행으로 502 timeout을 낸 전례가 있다 (2026-10-26, 30초 초과 추정) | 긴 순차 체인(전사→LLM→TTS 전체 대기)은 타임아웃을 부른다. 스트리밍(SSE)·청크 분할이 구조적으로 필요하다 |
| 배치 모델만 | Workers AI의 Whisper·MeloTTS는 파일/텍스트 전체를 받아 전체 결과를 돌려준다. 스트리밍 변형이 아니다 | 부분 전사·스트리밍 TTS는 모델이 직접 주지 않는다. 청크 분할로 흉내 내는 설계만 가능하다 |
| 무료 티어 공유 한도 | 10,000 neurons/일, Clef 라우터·요약 등 모든 Workers AI 용도와 공유 | 실시간은 호출 횟수가 늘어난다. 2단계 전에 분당 뉴런 예산을 계산하고, 상한 정책을 다시 정의해야 한다 |
| CPU 시간 제한 | Worker 1회 실행의 CPU 시간에 상한이 있다 (Free 티어 기준) | 오디오 처리(디코딩·리샘플링)를 Worker 안에서 무겁게 하지 않는다. 가능한 한 브라우저 측에서 전처리한다 |

## 3. LiveKit agents-js 주의 + 브라우저 WebRTC 방향

근거: 조사 문서 2-6절. `livekit/agents-js` ★951 · Apache-2.0 · 2026-10-25 기준 이슈 502건.
★ 대비 이슈가 많아 **TS 버전의 성숙도가 낮아 보인다**는 것이 조사 문서의 판정이다.

### 3.1 TS 서버 도입 보류

- `agents-js`는 **서버용** 에이전트 런타임이다. MyHub의 Worker에 TS 에이전트 서버를 올리는 방식은
  이 문서 시점에서는 검토하지 않는다. 이유 두 가지다.
  1. **성숙도**: 이슈 502건 / ★951은 비율로도 높다. 서버 런타임의 결함은 음성 파이프라인 전체를 멈추게 한다.
  2. **환경 부합**: LiveKit Agents 서버는 지속 프로세스·실시간 미디어 처리를 전제로 한다. Workers의
     단발·무상태 실행 모델과 맞지 않는다.
- **결정: TS 서버 도입 보류, 패턴만 참고.** agents-js의 턴테이킹·인터럽션 처리 방식은
  2.2절의 상태머신을 구현할 때 대조군으로 삼는다. 코드 복사나 의존성 추가는 하지 않는다.

### 3.2 브라우저 쪽 WebRTC 전송 — 검토 방향만

- 브라우저와 서버 사이에 실시간 오디오를 흘려보내려면 WebRTC가 정석이다. LiveKit의 **TS 클라이언트 SDK**는
  이 용도로 검토할 수 있다. 단, 이것은 "서버 도입"이 아니라 "브라우저 전송 계층" 검토다.
- **검토 전에 정할 것**:
  1. 상대방이 누구인가 — WebRTC는 피어(서버)가 있어야 한다. MyHub에는 미디어 서버가 없다.
     LiveKit Cloud 같은 외부 미디어 서버를 쓰면 카드·과금·개인정보(음성이 제3자 서버를 경유) 문제가 생긴다.
     사용자 원칙(카드 없는 무료 티어 고수)과도 충돌한다.
  2. 대안이 있는가 — 2단계 1차 목표(VAD 자동 종료 + 인터럽션)는 WebRTC 없이도 가능하다.
     브라우저에서 VAD → 청크 업로드 → Worker 배치 호출 → 청크 재생의 구조면 된다.
     WebRTC는 "지속 오디오 스트림"이 필요해질 때만 다시 검토한다.
- **결론**: 브라우저 WebRTC 전송은 **2단계 1차 범위 밖**이다. TS 클라이언트 SDK 검토는
  미디어 서버를 둘지 말지의 결정이 선행된 뒤에 한다.

## 5. MyHub 음성 2단계 로드맵

### 5.1 단계 정의

| 단계 | 내용 | 상태 |
| --- | --- | --- |
| **1단계 (현행)** | 단발 전사 + 합성. 녹음(버튼) → 전사 → 채팅 → 합성 → 재생. VAD·스트리밍·인터럽션 없음 | 구현됨 (`cc0c60a`). **라이브 미검증 (NOT TESTED)** |
| **2단계 (목표)** | 스트리밍·인터럽션. VAD 자동 종료 → LLM 스트리밍 → 문장 단위 TTS 청크 재생 → 개입 시 즉시 중단·컨텍스트 절단 | 설계만 (이 문서). 미구현 |

### 5.2 2단계 진입 순서 (순서를 바꾸면 동작하지 않는다)

1. **1단계 실기기 검증** — iOS PWA에서 녹음(mp4) → 전사 → 재생 종단 테스트. MeloTTS 출력 포맷(wav vs mp3),
   Whisper 한국어 정확도를 실측으로 확정한다. 이것이 안 되면 2단계는 그 위에 쌓을 수 없다.
2. **LLM 스트리밍 (SSE)** — `/api/ai/chat`에 스트리밍을 먼저 넣는다. 텍스트 채팅에서 동작을 확인한 뒤에
   음성이 그것을 쓴다. 음성만의 스트리밍을 따로 만들지 않는다.
3. **VAD 자동 종료 (브라우저 측)** — 버튼 종료를 VAD 종료로 바꾼다. 임계값·무음 지속 시간은 실측으로 정한다.
   이 단계만으로도 "녹음하고 기다리는" 단발 흐름은 유지되나, 사용자 경험은 크게 좋아진다.
4. **문장 단위 TTS 청크 재생** — 응답 전체 합성을 문장 단위 합성 + 순차 재생으로 바꾼다. 일일 상한 정책을
   "요청 수"에서 "문장 청크 수" 기준으로 다시 정의한다. iOS 연속 재생 동작을 실기기로 검증한다.
5. **인터럽션** — `SPEAKING` 중 VAD 감지 → 재생 중단 → LLM 스트림 중단 → 컨텍스트 절단(재생된 부분까지만 기록).
   (2)~(4)가 전제 조건이다. 에코 오탐 테스트를 포함한다.

2단계 1차 목표는 **(3) VAD 자동 종료 + (5) 인터럽션**이다. 부분 전사는 2.2절 (2)에서 정리한 대로
비용·정확도 손해가 있어 1차 범위 밖이며, 스트리밍 STT 단가를 다시 계산한 뒤에 결정한다.
WebRTC 전송은 2단계 1차 범위 밖이다 (3.2절).

### 5.3 각 단계의 전제 조건

| 전제 조건 | 내용 | 상태 |
| --- | --- | --- |
| 무료 티어 한도 | 10,000 neurons/일 공유. 2단계는 호출 횟수가 늘어나므로, 단계별로 분당 뉴런 예산을 계산하고 상한 정책을 다시 정의해야 한다 | 미계산 — 2단계 설계 시 필수 |
| Workers 제한 | 30초 edge 제한(추정), 배치 모델만, 단발 요청 구조 | 2.2절 (3)·(4)의 스트리밍·청크 분할이 구조적 대응. Durable Objects WebSocket은 별도 검토 필요 |
| 테스트 방법 | 각 단계마다 실기기(iOS PWA) + 라이브 종단 테스트가 필요하다. mock·로컬 테스트만으로는 VAD 임계값·iOS 연속 재생·에코 오탐을 검증할 수 없다 | 미수행 — 1단계부터 실기기 검증이 밀려 있다 |
| 개인정보 경계 | 1단계와 동일: 오디오 저장 없음, 전사 텍스트는 일반 텍스트 입력과 동일 취급, 잠긴 메모에 닿지 않음. 2단계에서 오디오 청크를 더 자주 보내도 저장 정책은 바뀌지 않는다 | 1단계 정책 유지 |

### 5.4 테스트 방법 (단계별)

- **1단계**: iOS 실기기에서 녹음 → 전사 → 채팅 → 합성 → 재생 종단. Whisper 한국어 정확도(실제 대화 문장),
  MeloTTS 출력 포맷, 60초 상한·429·503 폴백 동작을 확인한다.
- **VAD**: 조용한 방·소음 있는 방·짧은 말·긴 침묵의 4가지 조건에서 종료 시점을 측정한다. 말 중간 끊김과
  응답 지연을 함께 기록한다.
- **LLM 스트리밍**: 첫 토큰까지의 시간, 문장 경계 절단의 오절단 여부(숫자·약어·URL 포함 문장)를 확인한다.
- **TTS 청크 재생**: 문장 간 끊김·억양 깨짐 여부, iOS에서 두 번째 이후 청크가 자동 재생되는지를 실기기로 확인한다.
- **인터럽션**: 재생 중 말을 시작했을 때 재생이 멈추는 시간(목표: 체감 즉시), 중단 후 대화 기록에 남은
  비서 응답이 실제 재생분과 일치하는지, 기침·소음에 오탐하지 않는지를 확인한다.
- **공통**: 각 단계마다 뉴런 사용량을 `GET /api/voice/status`로 확인하고, 100회 상한·무료 티어 안에서
  동작하는지를 기록한다.

## 6. 결정 필요 사항 (이 문서에서 정하지 않은 것)

1. **VAD 구현 방식** — Web Audio API 임계값 vs wasm 경량 모델. 번들 크기·iOS 동작·정확도를 비교한 뒤 결정.
2. **무음 지속 시간** — 발화 종료로 보는 무음 길이. 실측으로 정할 값이며, 설정으로 뺄 것.
3. **컨텍스트 절단 단위** — 인터럽션 시 부분 재생된 문장을 어떻게 처리할지 (재생분까지만 남기기 vs 문장 단위 버리기).
4. **상한 정책 재정의** — 문장 청크 재생 시 일일 상한을 "요청 수"가 아니라 무엇으로 셀지 (문장 수 / 뉴런 / 오디오 분).
5. **부분 전사 여부** — 스트리밍 STT 단가(Deepgram nova-3 836.36 neurons/분 등)를 다시 계산한 뒤 결정.
   현행 판정은 1차 범위 밖이다.
6. **Durable Objects WebSocket 도입 여부** — 지속 오디오 스트림이 필요해질 때만 검토. 2단계 1차 범위 밖이다.
7. **fish-speech 라이선스 직접 확인** — 교체 검토 시에만 필요. 현행은 MeloTTS 유지라 당장 하지 않는다.

## 7. NOT TESTED / 미검증 목록

- MeloTTS 출력 포맷 (wav vs mp3) — 라이브 호출로만 확정. 코드는 매직 바이트로 양쪽 대응.
