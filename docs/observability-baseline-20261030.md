# 관측 기준선 리포트 — 귀속(0065) 이전 소급 산출 + 귀속 이후 현황

- 작성일: 2026-10-30
- 트랙: 관측 기준선 리포트 (문서 only — 코드 수정·배포 없음)
- 데이터 출처: 운영 D1 `ai_usage`를 `.scratch/d1q.py`(읽기 전용)로 직접 조회한
  실측만 사용한다. 추정·외삽·표본 없는 비율 일반화는 하지 않으며, 모든
  비율에 표본 수(n)를 병기한다.
- 조회 시점의 전체 행 수: **1,115행** (id 1~1115). 그중 귀속 이전(레거시)
  1,111행 + 귀속 이후 4행으로 갈린다 (§1·§2의 경계 정의 참조).
- 선행 문서:
  - FC 전환 계획·단계 0 정의: `docs/fc-transition-plan-20261029.md`
    (§3.0 관측 동등성, §4 단계 0 — "마커 기준선: 전 비서 2주간 측정")
  - 게이트 정책 동등성: `docs/gate-policy-equivalence-20261030.md` (§4에서 요약)
  - 지표 산출 코드: `src/services/ai-metrics.ts`
    (`GET /api/ai/metrics`, §3에서 사용법)

## 0. 방법과 경계 정의

- **레거시(귀속 이전) 행**: `engine IS NULL AND persona IS NULL`인 행.
  마이그레이션 0065(`migrations/0065_ai_usage_attribution.sql`)는 기존 행을
  소급하지 않으므로, 0065 적용·귀속 코드 배포 이전의 행은 전부 이 조건에
  해당한다. 실측 1,111행 (id 1~1111).
- **귀속 이후 행**: `engine` 또는 `persona`가 NULL이 아닌 행. 실측 4행
  (id 1112~1115). engine·persona 중 하나만 NULL인 행은 0건이었다.
- **성공 판정**: 지표 API와 동일하게 `ai_usage.outcome` 기준 —
  `success`만 성공, `failed`·`rate_limited`·기타는 비성공으로 센다.
- **지연 백분위**: 지표 API와 동일한 nearest-rank 방식
  (`src/services/ai-metrics.ts`의 `percentile`)으로, 조회한 `latency_ms`
  전체 값에서 계산했다 (SQL 근사 아님). `latency_ms`는 스키마상 NOT NULL이라
  레거시 1,111행 전부에 값이 있다.
- 시각은 DB에 저장된 UTC(ISO `Z`)를 그대로 표기하고, 필요한 곳에만
  KST(+9h)를 병기한다.

#### 비서별·엔진별 분해는 레거시 행으로 불가능하다 (근거)

`capability`를 비서로 환산할 수 없는 이유를 코드와 데이터 양쪽으로 확인했다.

코드 근거:

1. 채팅 경로에서는 비서→capability 매핑이 1:1로 보인다 —
   `src/modules/ai/prompt-helpers.ts`의 `PERSONA_POLICY`와
   `src/services/expert-registry.ts`의 `EXPERTS`가 concierge=chat,
   keeper=summarize, builder=code, scheduler=schedule로 대응한다.
   **그러나 `ai_usage`에 기록되는 호출이 전부 채팅 경로에서만 오지 않는다.**
2. 비서 없는 capability 호출이 실제로 존재한다 —
   `src/services/news-briefing.ts:103-118`의 기본 요약기는 "personaId 없음 →
   FC 도구 미부착"을 명시하고 `capability: 'summarize'`로 `aiChat`을 호출한다.
   이 행들은 summarize로 기록되지만 에코(keeper)의 행이 아니다.
   `src/scheduled.ts` 머리 주석도 "persona 없는 capability 호출"을 예약
   경로의 원칙으로 명시한다.
3. capability 값 자체가 비서 집합과 다른 어휘를 포함한다 —
   E3 경로의 `src/ai/run-logger.ts`는 capability를 `'function_calling'`으로
   고정해 기록하고, `src/ai/fallback-controller.ts:153`는 `'fc-chat'`,
   `src/ai/model-router.ts:504`는 `'fallback'`을 쓴다. 즉 capability는
   "작업 종류 라벨"이지 비서 식별자가 아니다. (레거시 실측에서는 이 값들이
   0건이라 위 표에 나타나지 않을 뿐이다.)
4. `src/services/ai.ts`의 모델 선택도 capability를 비서와 독립적으로
   소비한다 — 예: builder 직접 경로는 `personaId === 'builder'` **또는**
   `capability === 'code'` 중 하나만 성립해도 탄다(`ai.ts:601` 부근).
   code 행이 전부 노바(builder)의 행이라고 단정할 수 없는 구조다.

데이터 근거 (provider × capability 교차표, 레거시 1,111행):

| capability | gemini | groq | nvidia | workers-ai |
|---|---:|---:|---:|---:|
| chat | 212 | 75 | 0 | 1 |
| summarize | 24 | 9 | 91 | 276 |
| code | 109 | 25 | 140 | 0 |
| schedule | 0 | 149 | 0 | 0 |

- 비서의 프로바이더 핀은 고정인데(루미·노바=gemini, 에코=현행 workers-ai,
  캘리=groq — `expert-registry.ts`), summarize가 4개 provider 전부에서,
  chat이 groq(캘리의 핀)에서 75건, code가 nvidia에서 140건 기록돼 있다.
  핀 변경 이력과 폴백·유틸 호출이 섞인 결과이며, 어느 provider 조합으로도
  capability 행을 특정 비서에게 귀속시킬 수 없다.
- schedule만 groq 단일 provider로 나타나지만, 이것도 "캘리 = schedule
  149건"이라는 등식을 보장하지 않는다 (비서 없는 schedule 호출과 캘리의
  비-schedule 호출을 이 테이블만으로 분리할 방법이 없다).

**엔진별 분해도 같은 이유로 불가능하다.** 레거시 행에는 engine 기록 자체가
없고, E1(마커)/E2(내장 FC) 여부는 provider·capability 어느 조합으로도
재구성할 수 없다 (E2 도달 조건은 persona=keeper + provider 게이트의
교집합인데, 레거시 행에는 persona가 없다). 따라서 이 절의 수치는
**provider/model/capability 차원의 소급 산출이 한계**이며, 비서별·엔진별
수치는 §2의 귀속 이후 행이 누적된 뒤에야 처음 성립한다.

### 1.5 trace_id 기반 폴백 근사 (레거시)

지표 API와 동일 정의(`countFallbackTraces`): 같은 trace_id 안에서 비성공
행 뒤에 성공 행이 다시 오면 "폴백으로 회복된 턴"으로 세며, 트레이스당
최대 1건이다. 실제 폴백 메커니즘의 직접 기록이 아니라 근사다.

| 항목 | 실측값 |
|---|---:|
| trace_id가 있는 레거시 행 | 127 / 1,111 |
| 서로 다른 trace_id | 90 |
| 비성공 행이 1개 이상 있는 트레이스 | 9 |
| 그중 뒤에 성공 행이 온 트레이스 (회복 근사) | 9 |
| 회복률 (위 두 수의 비율) | 9/9 = 100% — **일반화 금지, 아래 참조** |

- **커버리지가 극히 좁다.** trace_id는 레거시 행 중 id 985
  (2026-10-26T08:52:32.783Z)부터 처음 나타나며, 전체 비성공 행
  401건(291+110) 대부분은 trace_id가 없어 이 근사의 대상 자체가 아니다.
- 따라서 "회복률 100%"는 trace가 남은 최근 구간의 실패 트레이스 9개에
  대한 서술일 뿐, 전체 기간 폴백 성능의 기준선으로 쓰면 안 된다.

### 이 수치를 "기준선"이라 부르지 않는 이유와, 기준선 성립 조건

- FC 전환 계획 단계 0의 산출물은 "전 비서 **2주간** 도구 성공률"이다
  (`docs/fc-transition-plan-20261029.md` §4 단계 0). 귀속 시작일은
  2026-10-30이므로, 기간 조건만으로도 **2026-11-13 이전에는 기준선이
  성립할 수 없다.**
- 표본 조건도 없다. 비서당 1~2건(keeper의 2건은 같은 trace의 연속
  호출)으로는 성공률·지연 어느 것도 비서의 특성으로 읽을 수 없고,
  builder는 표본 자체가 0건이다. 계획 §3.2도 단일 사용자 시스템의
  표본 부족을 명시하며, 백분율 기준은 "기준선 대비 명백한 하락이
  없는가"의 경보선으로만 쓰라고 한정한다. 참고 하한으로, 계획 §4
  단계 3의 관측 조건(최소 2주 **그리고** 비서별 최소 100턴)을
  기준선 재측정 시점의 표본 참고치로 제안한다.
- **재측정 제안**: 2026-11-13(귀속 시작 +2주) 이후에 1차로 이 절을
  다시 산출하되, 그 시점에 비서별 표본이 100턴에 크게 못 미치면
  기간을 연장하고 "표본 부족"을 명시한 채 기준선 확정
을 미룬다.
  재측정 시에는 §1.2~1.3 형식의 provider/model 표와 함께, 귀속 행만으로
  비서별 × 엔진별 표를 처음 추가한다.

## 3. 지표 API 사용법 — `GET /api/ai/metrics`

- 경로: `GET /api/ai/metrics` (구현: `src/modules/ai/admin-routes.ts:420`,
  산출 로직: `src/services/ai-metrics.ts`의 `getAiMetrics`).
- 인증: 별도 전용 인증은 없고, 사이트 전역 인증 미들웨어 뒤에 있다 —
  유효한 세션 쿠키(`myhub_session`)가 없으면 API는 401을 반환한다
  (`src/index.ts`의 전역 미들웨어; `/api/ai/metrics`는 미인증 allowlist에
  없다).
- 파라미터: `days` 1개. 기본값 14, 1~90으로 클램프되며 숫자가 아니면
  기본값 14를 쓴다 (`parseMetricsDays`, `METRICS_DEFAULT_DAYS=14`,
  `METRICS_MAX_DAYS=90`). 즉 이 API로는 최대 90일까지만 소급 집계할 수
  있고, §1처럼 전체 기간(2026-10-08~)을 보려면 D1 직접 조회가 필요하다.
- 기간 필터는 `created_at >= datetime('now', -days days)`이며, 집계 대상
  테이블은 `ai_usage`·`ai_error_log`·`tool_execution_audit`·
  `tool_approval_requests`다.

응답 구조 요약 (`{ ok: true, ... }`로 감싸서 반환):

| 필드 | 내용 |
|---|---|
| `days`, `generatedAt` | 적용된 기간(일)과 생성 시각 |
| `schema` | `aiUsageTable`, `aiUsageEngineColumn`, `aiUsagePersonaColumn`, `approvalExecutedAtColumn` 존재 여부 + `note`. 0065 미적용 DB에서도 500이 되지 않고 해당 차원을 `unknown` 버킷으로 접는다는 고지가 여기 실린다 |
| `usage.overall` | 기간 전체 합산 (아래 그룹 요약과 동일 형식) |
| `usage.byPersona` | persona별 그룹 요약. NULL·빈 값은 `unknown` |
| `usage.byEngine` | engine별 그룹 요약. 계약 어휘(`marker`·`builtin-fc`·`registry-fc`·`degraded`) 밖·NULL은 `unknown` |
| `usage.byProvider` | provider별 그룹 요약 |
| `fallback` | §1.5와 같은 trace_id 근사: `traceTurns`, `tracesWithFailure`, `recoveredTurns`, `recoveryRate`, `method`(근사 방법 설명), `approximate: true` |
| `errors` | `ai_error_log`의 기간 내 총건수와 provider별 분포 |
| `approvals.audit` | `tool_execution_audit` 총건수·action별 분포·`executed` 건수 |
| `approvals.requests` | `tool_approval_requests` 총건수·status별 분포·`executedClaimCount`(0063의 `executed_at`이 채워진 건수; 컬럼이 없으면 null + 사유) |
| `approvals.duplicateExecutionBlockedAttempts` | **항상 null** + 사유 (아래 참조) |
| `notes` | 성공 판정·백분위·폴백 근사 등 산출 정의 고지 배열 |

그룹 요약(`GroupSummary`)의 필드: `requests`, `success`, `failed`,
`rateLimited`, `other`, `successRate`, `failureRate`, `p50LatencyMs`,
`p95LatencyMs`, `inputTokens`, `outputTokens`, `totalTokens`, `neurons`.
응답 키는 camelCase다 (`byPersona`·`byEngine` 등).

### 산출 불가 지표 — 중복 실행 차단 시도

- `duplicateExecutionBlockedAttempts`는 값이 아니라 **null + 사유 문자열**
  로 반환된다 (`DUPLICATE_BLOCKED_REASON`). 0으로 위장하지 않는 것이
  이 API의 명시적 설계다.
- 이유: 0063의 `executed_at` 원자 선점(claim)은 성공한 호출 1건만
  기록으로 남기고, 선점에 실패한 재시도 호출은 `ai_usage`·
  `tool_execution_audit`·`tool_approval_requests` 어디에도 기록되지
  않는다. 따라서 "중복 실행이 몇 번 차단됐는가"는 현재 영속 기록이
  없어 산출할 수 없고, `executedClaimCount`는 "선점된 실행 수"일 뿐
  차단 시도 수가 아니다. 이 지표를 얻으려면 선점 실패 시점의 기록을
  새로 심는 별도 작업이 선행돼야 한다.

## 4. 게이트 동등성 요약 (원문: `docs/gate-policy-equivalence-20261030.md`)

원문 기준으로 요약한다. 원문의 실제 집계는 **일치 7개 그룹 · 불일치
D1~D5(+D5-보충) · 구조상 검증 불가 7개 구간**이다 — 불일치를 D1~D3까지로
줄여 읽으면 D4·D5의 구조적 취약성을 놓치므로, 이 절은 원문 목록 그대로
적는다. 고정 테스트는 `tests/gate-policy-equivalence.test.ts` 24건이다.

### 일치 7개 그룹 (테스트로 고정됨)

1. 잠긴 메모 읽기·검색 차단 — 공유 실행층(`ai-access`) 덕에 E1/E2 동일.
2. 잠긴 메모 삭제 차단 — 도달 경로는 다르나 결과 동일.
3. 잠긴 메모 수정 차단 — 결과 동일 (단 E2는 도구 자체가 없는 것이 이유).
4. 비대화형 origin 쓰기 규칙 — 규칙 자체는 동일, 읽기는 양쪽 허용.
5. restricted 외부 전송 차단·민감도 2+ 메모 본문의 모델 전송 차단 —
   공유 게이트라 구조적으로 동일.
6. 잠금/해제 도구 전면 차단 — 유효한 승인으로도 못 뚫는 점까지 동일.
   AI 경로에서는 잠금 해제 step-up(PIN)에 도달할 수 없다.
7. 형식 검증 fail-closed — 깨진 호출은 양쪽 모두 실행되지 않는다.

### 불일치 D1~D5의 실무 의미

| ID | 내용 | 실무 의미 |
|---|---|---|
| D1 | E2(운영 FC) 쓰기에 승인 게이트 없음 — E1·E3는 승인 필수, E2만 대화형이면 즉시 실행 | 최우선. 인젝션이 모델을 통해 쓰기를 유도해도 막을 승인 단계가 없다 (메모·cron·일정 생성). 삭제는 D3로 완결이 안 돼 피해가 제한적일 뿐이다 |
| D2 | 민감도 2(잠기지 않음) 메모의 삭제·수정 — E1 실행층은 `is_locked`만 봐서 승인 하에 실제 삭제·덮어쓰기가 가능, E2는 확인 단계에서 차단 | "읽기 불가 = 존재 숨김" 원칙과 쓰기 측 판정이 어긋난다. 무승인 삭제는 아니지만(승인 선행) 엔진별 판정이 갈린다 |
| D3 | 삭제 완결 방식 — E1은 승인 후 실제 삭제까지 완결, E2는 `confirmation_required` 반환이 끝이고 실제 삭제 수단이 FC 경로에 없음 | 보안이 아닌 기능 불일치. 후속 턴 완결이 고정 코드가 아니라 모델 행동에 의존한다 |
| D4 | E2 출처 게이트의 강제 위치 — 디스패처가 아닌 `ai.ts` FC 루프 인라인(하드코딩 7종 목록)이 유일한 강제 지점 | 구조적 취약성. 디스패처를 직접 부르는 새 호출자가 생기거나 신규 FC 쓰기 도구가 목록에서 누락되면 게이트가 통째로 빠진다 |
| D5 | 비서별 허용 목록 — E2 디스패처·preflight에 비서 강제가 없음. 경계는 `useFC` 게이트(keeper 한정)와 스킬 제공 목록뿐 | keeper 내부 도구 간 혼선 수준으로 제한되나, "비서별 허용"이라는 정책이 FC 경로에는 코드로 존재하지 않는다 |
| D5-보충 | keeper 일정 등록은 E2에만 있는 의도된 확장 (E1 목록에 없음) | 위험이 아닌 설계 결정의 비대칭. 동등성 논의에서 "버그"로 세면 안 된다 |

### 구조상 검증 불가 7개 구간 (원문 §"구조상 동등성 검증이 불가능한 구간")

1. E3 전체의 운영 동등성 — 4중 게이트로 운영 도달 불가, 단위 대조까지가 한계.
2. `ai.ts` FC 루프 인라인 게이트 — export되지 않아 단위 테스트 직접 호출 불가.
3. E1의 프롬프트 문법 의존 구간 — 게이트 도달 자체가 모델 출력에 확률적으로 의존.
4. E2의 도구 결과 재전송 — 실전송 여부의 종단 검증은 실모델 호출이 필요.
5. D3의 후속 턴 완결 — 모델의 다음 행동에 달려 결정적 테스트로 고정 불가.
6. E1 전용 도구군(Google 쓰기·아티팩트·할일 등) — E2 등가물이 없어 비교 자체가 불성립.
7. 운영 설정값 의존 구간 — 스킬 매칭·`ai_settings` 오버라이드 등 운영값을 봐야 확정되는 구간.

### 엔진 통합 판단 시 D1을 다루는 방법

D1은 "두 엔진의 판정이 다르다"는 수준의 차이가 아니라, **E2 쪽에
게이트 자체가 존재하지 않는다**는 비대칭이다. 잠긴 메모의 읽기·수정·
삭제 차단처럼 실행층에서 갈리는 판정(§일치 1~3)은 공유 실행층 덕에
통합 후에도 유지되지만, 쓰기 승인 게이트는 E1에만 있으므로, 통합을
"E2로 일원화"하는 순간 현행 E1이 제공하는 승인 카드 방어가 그대로
사라진다. 따라서 엔진 통합 판단에서는 D1을 통합 이후에 고칠 후속
과제로 미루지 말고 **선행 하드 게이트**로 다뤄야 한다: FC 경로에
E1과 동등한 승인 게이트(쓰기 ask·삭제 필수 승인)가 코드와 테스트로
고정되기 전에는 어느 비서도 FC 기본화로 넘기지 않으며(FC 전환 계획
§3.1의 C4·§5도 같은 취지), D2(민감도 2 메모 쓰기 판정의 실행층
불일치)도 같은 게이트 작업에서 함께 판정을 통일한다 — 잠긴 메모
쓰기 차단이 "일치"로 기록돼 있다고 해서 민감 메모 쓰기까지 동등한
것은 아니다.

## 6. 엔진 통합 판단에 남은 관측 — 체크리스트

기준선 확정과 엔진 통합(FC 전환 계획 §3.1의 C2 등) 판단 전에 남은
항목이다. 완료된 항목은 넣지 않았다.

- [ ] **관측 기간**: 귀속 시작(2026-10-30)부터 최소 2주 경과
      (최초 충족일 2026-11-13). 그 전에 뽑은 비서별·엔진별 수치는
      §2처럼 "현황"으로만 표기하고 기준선으로 부르지 않는다.
- [ ] **비서별 표본**: 비서 4명 전원의 귀속 행이 누적될 것.
      현재 builder 0건·나머지 1~2건 (§2). 재측정 시 비서별 n을
      병기하고, 계획 단계 3의 참고 하한(비서별 최소 100턴)에
      못 미치면 기준선 확정을 미룬다.
- [ ] **엔진별 표본**: marker·builtin-fc 외에 registry-fc·degraded
      행이 실제로 찍히는 경로가 있는지 확인할 것. 현재 두 값은
      0건이며, registry-fc는 E3가 운영 도달 불가라 운영 표본이
      안 쌓이는 것이 정상인지, degraded 진입 조건이 무엇인지부터
      코드로 확정해야 한다.
- [ ] **도구 단위 성공률의 부재 (현재 한계)**: 지금 지표는 전부
      `ai_usage`의 **LLM 호출 행 단위** outcome이다. E1/E2의 도구
      실행(어떤 도구가 몇 번 성공/실패했는가)은 행 단위 성공으로
      대체 측정 중일 뿐, 도구 단위 성공률은 아직 산출 수단이 없다.
      FC 전환 계획 §3.1 C2가 요구하는 "도구 실행 성공/턴"을 재려면
      도구 실행 결과의 구조화 기록이 별도로 필요하다.
- [ ] **폴백 근사의 커버리지**: trace_id가 없는 행이 레거시에서
      984/1,111건이었다 (§1.5). 귀속 이후 행에서는 trace_id가
      전 행에 찍히는지 재측정 때 확인할 것 — 안 찍히는 호출
      경로가 있으면 폴백 지표는 계속 부분 근사에 머문다.
- [ ] **중복 실행 차단 시도**: 영속 기록이 없어 산출 불가 (§3).
      이 지표가 통합 판단에 필요해지면, 선점 실패 기록을 심는
      작업이 선행돼야 한다.
- [ ] **토큰·뉴런 결측 구간**: 레거시에서 토큰 NULL 623행·뉴런은
      12행만 기록됐다 (§1.1). 귀속 이후 행에서 토큰·뉴런 기록률이
      provider별로 어떻게 달라졌는지 재측정 때 함께 집계할 것 —
      기록률이 낮은 provider의 비용 지표는 부분합으로 표기한다.
- [ ] **게이트 동등성의 미해결분**: D1(승인 게이트)·D2(민감도 2
      쓰기 판정)는 관측이 아니라 코드 작업으로 닫아야 하는 항목
      이며 (§4), 검증 불가 7개 구간 중 E3 운영 동등성·FC 루프
      인라인 게이트는 통합 설계가 정해져야 검증 방법이 생긴다.
      관측만으로는 이 항목들이 닫히지 않는다.
- [ ] **재측정 산출물**: 2026-11-13 이후 §2를 귀속 행 전체로
      다시 산출해 이 문서를 갱신하거나 후속 리포트를 만들고,
      그때 처음 "기준선"이라는 말을 쓴다. 비교 대상으로는 §1의
      provider/model 소급치(레거시 전체)와 귀속 이후치를 나란히
      두되, §1이 이질적 구간이라는 한계를 각 표에 유지한다.
