## 1. 장기 메모리 시스템 (비서가 사용자를 기억하는 구조)

### 1.1 핵심 개념 정리

| 구분 | 현재 MyHub | 장기 메모리 |
|------|-----------|------------|
| 저장 | `ai_chats` 테이블 (원본 대화 로그) | 추출된 **사실/선호/엔티티** (요약된 지식) |
| 검색 | Exa (외부 웹검색) | 과거 대화·사용자 지식에 대한 시맨틱 검색 |
| 범위 | 세션 내 | 세션 간, 수개월~수년 |

유명 오픈소스의 핵심 아이디어 (가볍게 가져올 부분만):

- **mem0**: 대화를 LLM이 읽고 "살아남을 가치가 있는" 사실만 추출 → 벡터 DB 저장 → 다음 대화에서 관련 메모리만 주입. `add()` / `search()` 두 함수면 동작. **MyHub에 가장 이식하기 쉬움.**
- **Zep (Graphiti)**: 시간(temporal) 지식그래프. 사실마다 "언제 알게 됐고, 언제까지 유효했는지" 기록. "예전엔 X 좋아했는데 지금은 Y" 같은 **변화 추적**에 강함.
- **Letta (구 MemGPT)**: 에이전트 자신이 메모리를 읽고 쓰는 OS식 구조. 전체 런타임을 바꿔야 해서 **MyHub에는 과도**.

**핵심 통찰**: 무거운 프레임워크 없이도 "mem0 미니멀 구현"은 Worker 안에서 가능. 구조:

```
대화 종료 시 (비동기) → LLM(작은 모델, 예: Workers AI llama-3.2-1b)이 메모리 후보 추출
→ 임베딩(bge-m3 / embeddinggemma) → Vectorize 또는 D1 저장
다음 대화 시 → 질문 임베딩 → 유사 메모리 top-k → 시스템 프롬프트에 주입
```

### 1.2 "어제 말한 그거" 같은 참조 해결 (entity resolution)

순수 벡터 검색만으로는 "그거" 같은 대명사/지시어를 해결 못 함. 검증된 경량 패턴:

1. **엔티티 정규화**: 메모리 저장 시 LLM이 고유명사(사람·프로젝트·장소)를 추출해 `entities` 컬럼에 저장. 검색 시 질문 속 명사와 매칭.
2. **대화 컨텍스트 윈도우 우선**: "그거"는 최근 대화일 확률이 90% 이상 → 최근 N턴을 먼저 보고, 없으면 장기 메모리로 폴백.
3. **mem0식 ADD/UPDATE/DELETE 분류**: 새 대화마다 기존 메모리와 비교해 "추가·갱신·삭제" 판단 (이미 MyHub의 events 버스 + D1 패턴과 궁합 좋음).
4. **Zep식 시간 필터**: `ai_memories` 테이블에 `valid_from`, `valid_to`, `superseded_by` 컬럼. 최신 사실만 기본 검색.

**추천 설계 (D1만으로, Vectorize 없이도 시작 가능)**:

```sql
CREATE TABLE ai_memories (
  id INTEGER PRIMARY KEY,
  persona TEXT,            -- 루미/에코/노바/캘리 또는 'shared'
  fact TEXT,               -- "사용자는 아이폰 PWA를 쓴다"
  category TEXT,           -- preference / project / person / routine / decision
  entities TEXT,           -- JSON 배열 ["아이폰", "PWA"]
  importance REAL DEFAULT 0.5,
  created_at TEXT,
  updated_at TEXT,
  superseded_by INTEGER,   -- 대체된 메모리는 여기서 연결
  embedding BLOB           -- 선택: 벡터 검색 원하면 추가
);
CREATE VIRTUAL TABLE ai_memories_fts USING fts5(fact, entities);
```

FTS5 + entities 매칭이면 한국어 환경에서 벡터 없이도 80% 해결됨 (메모 모듈의 FTS5+LIKE 폴백 패턴 재사용 가능).

### 1.3 Cloudflare Vectorize 무료 한도 (2026-10 기준, 공식 문서 확인)

- **무료 할당**: 월 3,000만 queried dimensions / 월 500만 stored dimensions
- **인덱스**: 계정당 100개, 인덱스당 최대 2,000만 벡터, 차원 최대 1,536
- **무료 네임스페이스**: 인덱스당 1,000개
- 체감 계산: bge-m3(1024차원)으로 1만 개 메모리 저장 → 1,024만 stored dims 중 약 1,000만 → 한도 내. 하루 100회 검색 × (1만 벡터 + 질의) × 1024차원 ≈ 1,000만 queried dims/일?? 주의: queried dims는 `(저장 벡터 수 + 쿼리 수) × 차원`. 1만 벡터 × 1024차원 = 1,024만/쿼리 → 하루 3회면 3,000만/월 한도 소진. **즉, 메모리 개수가 늘면 조회 한도가 빡빡해짐.**
- 결론: **벡터 없이 FTS5로 시작 → 메모리 1,000개 이상 쌓이고 나서 Vectorize 도입 검토**. 임베딩도 Workers AI 무료 뉴런(하루 1만) 안에서 가능.

### 1.4 항목 평가

| 항목 | 내용 |
|------|------|
| **적용 난이도** | **중** (FTS5 기반이면 중, Vectorize 포함이면 상) |
| **예상 효과** | **대** — "지난주에 얘기한 그 API 키" 같은 대화가 가능해지면 비서 체감이 완전히 달라짐. 캘리(일정)의 반복 업무 파악, 에코의 사용자 스타일 학습에 직결 |
| **무료 원칙 충돌** | **없음** — D1 무료 한도(5GB, 일 500만 행 읽기) 내, Vectorize도 무료 할당 내. LLM 추출은 기존 Gemini/Groq 키 사용 |

**주의**: 메모리 3단계 잠금(사용자 요구: 메모/첨부/블록)과 같은 보안 경계가 메모리에선 **더 중요**. API 키·카드번호 같은 민감 정보가 메모리에 추출되지 않도록 추출 프롬프트에 차단 규칙 필수.

## 2. Proactive 기능 (비서가 먼저 움직이는 것)

### 2.1 구현 패턴

| 기능 | 트리거 | 구현 방식 |
|------|--------|----------|
| 아침 브리핑 | Cron (매일 07:00 KST) | 일정 D1 조회 + 어제 대화 요약 → 푸시/인앱 카드 |
| 일정 리마인드 | Cron (15분 간격) | 30분 이내 시작 일정 조회 → 해당 사용자에게만 푸시 |
| 할일 nudge | Cron (매일 저녁) | 3일 이상 방치된 할일 → "아직 안 하셨네요" 푸시 |
| 주간 회고 | Cron (일요일) | 이번 주 완료/미완료 통계 → 에코가 요약 |

**설계 원칙** (검증된 패턴):
- **멱등성 필수**: Cron은 재실행될 수 있음. `(rule_id, 날짜)` 유니크 키로 중복 발송 방지.
- **조용한 기본값**: 사용자가 켠 것만 동작. nudge는 `cooldown`(하루 최대 N회) 필수 — 스팸이 되면 신뢰 붕괴.
- **발송 전 LLM 1회 호출**: "리마인드 문구를 자연스럽게" — 템플릿이 아닌 비서 말투로.

### 2.2 Cloudflare Workers Cron Trigger 무료 플랜 (2026-10 기준, 공식 문서 확인)

- **무료 플랜 지원: 예.** 계정당 **5개**까지 (유료는 250개).
- 최소 간격: **1분**.
- 시간대: **UTC 기준** (KST 변환은 코드에서 처리: `07:00 KST = 22:00 UTC 전날`).
- **주의**: 무료 플랜 Cron 호출당 **CPU 10ms** 제한. → 무거운 LLM 호출은 `ctx.waitUntil()`로 백그라운드 처리, 또는 fetch API로 분리.
- Cron 이벤트는 `scheduled(event, env, ctx)` 핸들러에서 처리. 무료 플랜 재시도 없음 → 중요 알림은 2개 슬롯(예: 07:00 + 07:15)으로 이중화 고려.
- **MyHub 5개 슬롯 배분안**: (1) 아침 브리핑 07:00 KST, (2) 일정 리마인드 */15분, (3) 저녁 할일 nudge 21:00 KST, (4) 주간 회고 일요일 20:00, (5) 예비 1개.

### 2.3 푸시 알림 무료 옵션

**Web Push (W3C 표준) — 완전 무료, 카드 불필요**:
- 방식: VAPID 키 쌍 자체 생성(무료) → 브라우저 Push API로 구독 저장(D1) → 서버에서 직접 암호화 발송. Firebase/OneSignal 같은 **제3자 서비스 불필요**.
- **iOS 16.4+**: 홈 화면에 추가된 PWA에서 Web Push 지원 (MyHub는 이미 iOS PWA — 조건 충족).
- 제약: iOS는 **반드시 보이는 알림**이어야 함 (조용한 백그라운드 푸시 불가). 사용자가 알림 권한을 허용해야 함.
- Workers에서 발송: WebCrypto로 VAPID 서명 + 페이로드 암호화 (RFC 8291/8292). 순수 JS 라이브러리로 구현 가능 — 별도 서비스 가입 없음.

**대안 (무료)**:
- 인앱 알림함: 푸시 권한 거부 시 폴백. D1 `notifications` 테이블 + 상단바 벨 아이콘. 구현 가장 쉬움.
- 이메일: 이미 Resend 연동됨. 다만 Resend 무료 한도 확인 필요.

### 2.4 항목 평가

| 항목 | 내용 |
|------|------|
| **적용 난이도** | **중** (Cron 5개 배분 + Web Push VAPID 구현. 인앱 알림함만이면 하) |
| **예상 효과** | **대** — "진짜 비서" 체감의 핵심. 아침 브리핑 하나만 잘 돼도 사용 빈도가 바뀜 |
| **무료 원칙 충돌** | **없음** — Cron 무료, Web Push 표준 무료. 단, 브리핑 생성용 LLM 호출은 기존 무료 키로 충당 |

**주의**: Cron은 UTC라 KST 변환 실수 주의. 5개 슬롯 제한 때문에 "일정 리마인드 15분 간격"이 1슬롯을 통째로 씀 — 슬롯 배분은 기획 단계에서 확정 필요.

## 3. 음성 인터페이스

### 3.1 STT (음성→텍스트) 무료 옵션

| 옵션 | 비용 | 한국어 | 비고 |
|------|------|--------|------|
| **브라우저 Web Speech API** (`SpeechRecognition`) | 완전 무료 | `lang='ko-KR'` 지원 (Chrome/Edge; Safari 14.5+ 부분 지원) | 키 불필요. 단, iOS PWA에서 불안정, Firefox 미지원. Chrome/Edge에서는 실전 가능 |
| **Workers AI Whisper** (`@cf/openai/whisper`) | 무료 (뉴런 한도 내) | 다언어 지원 (multilingual) | 하루 1만 뉴런. 커뮤니티 추산 하루 수백 회 음성 명령 가능. `@cf/openai/whisper-tiny-en`은 영어 전용이라 제외 |
| **Workers AI Deepgram Flux** (`@cf/deepgram/flux`) | 무료 (뉴런 한도 내) | 확인 필요 | 대화형 음성 에이전트용 신규 모델 |

**권장**: 1차 = 브라우저 Web Speech API (무료·즉시·서버 부하 0), 2차 폴백 = Workers AI Whisper (iOS PWA에서 Web Speech가 막힐 때).

### 3.2 TTS (텍스트→음성) 무료 옵션

| 옵션 | 비용 | 한국어 | 비고 |
|------|------|--------|------|
| **브라우저 speechSynthesis** | 완전 무료 | iOS Siri 한국어 음성, Chrome 한국어 음성 지원 | 키 불필요. 음질은 OS 음성에 의존. iOS PWA에서 동작 |
| **Workers AI MeloTTS** (`@cf/myshell-ai/melotts`) | 무료 (뉴런 한도 내) | 한국어 음성 1종 포함 | 뉴런 소모가 매우 적음 ("하루 종일 읽어도 무료 한도 내" 수준) |
| **Workers AI Deepgram Aura** (`@cf/deepgram/aura-1`, `aura-2`) | 무료 (뉴런 한도 내) | 영어 중심 (aura-2-es는 스페인어) | 한국어 답변용으로는 부적합 |

**권장**: 1차 = 브라우저 speechSynthesis (무료·즉시), 2차 = MeloTTS (음질이 아쉬울 때).

### 3.3 모바일 PWA에서 음성 호출 UX 패턴

검증된 패턴 (2026년 기준):

1. **버튼 탭 → 말하기** (가장 현실적): 채팅 입력창 옆 마이크 버튼 → `SpeechRecognition` 시작 → 중간 결과 실시간 표시 → 종료 시 전송. iOS에서는 사용자 제스처 필수라 이 패턴이 강제됨.
2. **읽어주기 토글**: 비서 답변마다 🔊 버튼 → speechSynthesis로 재생. "아침 브리핑 읽어줘" 같은 Proactive 기능과 연계 시 효과적.
3. **웨이크워드("헤이 루미")**: 브라우저만으로는 **불가능** (백그라운드 마이크 접근 불가). 네이티브 앱(Capacitor 등)이 필요 — MyHub 범위 밖. **고려하지 말 것.**
4. **음성 대화 모드**: STT → LLM → TTS 파이프라인을 연속 루프로. 응답 지연이 2~4초 수준이라 "전화 통화" 느낌보다는 "워키토키" UX로 설계.

**iOS PWA 주의사항**:
- Web Speech API 음성인식은 iOS Safari 14.5+에서 "부분 지원" — PWA(standalone) 모드에서 불안정하다는 보고 다수. **iOS에서는 Whisper 폴백이 사실상 필수.**
- speechSynthesis(TTS)는 iOS에서 안정적. 단, 첫 재생은 사용자 제스처 이후여야 함.
- 마이크 권한: HTTPS 필수 (이미 충족).

### 3.4 항목 평가

| 항목 | 내용 |
|------|------|
| **적용 난이도** | **하** (브라우저 API만이면 하. Whisper 폴백 포함이면 중) |
| **예상 효과** | **중** — 운전 중·요리 중 같은 상황에서 유용. 다만 데스크톱 사용이 주면 체감은 제한적 |
| **무료 원칙 충돌** | **없음** — 브라우저 API 완전 무료, Workers AI도 무료 뉴런 내 |

**주의**: 한국어 STT 정확도는 Chrome의 Google 백엔드가 가장 좋음. Whisper 한국어 품질은 양호하나 30초 단위 청크 처리라 긴 발화는 분할 로직 필요.

## 4. 품질 측정

### 4.1 비서 답변 자동 평가 방법

**LLM-as-judge** (업계 표준 패턴):
- 답변 생성 모델과 **다른(또는 같은 계열의 작은) 모델**이 루브릭 기준으로 1~5점 채점.
- MyHub 적용: 비서 답변 D1에 저장된 것을 배치(Cron)로 읽어 → Gemini/Groq 저비용 모델(2.5-flash-lite 등)이 채점 → `ai_quality_scores` 테이블에 기록.
- 평가 축 (비서별 맞춤):
  - 루미(대화): 자연스러움, 맥락 이해, 말투 일관성
  - 에코(요약): 충실도(원문 왜곡 없음), 간결성
  - 노바(코드): 정확성, 실행 가능성
  - 캘리(일정): 시간·날짜 정확성 (할루시네이션 치명)
- **판정자 편향 주의**: 같은 모델이 생성+채점하면 점수가 부풀려짐. 생성 모델과 다른 계열(Gemini 생성 → Groq 채점)로 교차하는 게 원칙.

**판정 없이 되는 경량 지표** (LLM 호출 없이):
- 검색 파이프라인: Exa 출처 수, 출처 클릭률
- 대화: 사용자 재질문율 ("아니, 그게 아니라" 패턴), 대화 중단율
- 응답 지연, 토큰 사용량, 폴백 발생률

### 4.2 사용자 피드백 수집 → 개선 루프

```
[답변 하단 👍/👎 버튼] → D1 ai_feedback 저장
    → 주간 Cron이 👎 답변 + LLM-as-judge 저점 답변 집계
    → 에코가 "이번 주 실패 패턴" 리포트 생성
    → 프롬프트/라우팅 규칙 수정 (사람이 승인)
    → 다음 주 점수와 비교 (회귀 감지)
```

- 👍/👎는 가장 저렴하고 효과적인 신호. 채팅 UI에 버튼 2개면 됨.
- 👎 클릭 시 선택적 사유 입력 ("틀렸어요 / 불친절해요 / 너무 길어요") — 사유별 집계가 개선 방향을 정해줌.
- **자동 프롬프트 수정은 금지** (사용자 원칙: 검토 게이트). 리포트까지만 자동, 적용은 사람 승인.

### 4.3 가벼운 평가 파이프라인 사례

검증된 미니멀 패턴 (오픈소스 `llm-eval` 스타일):

1. **골든 데이터셋**: 비서별 20~30개 대표 질문 + 기대 답변 요점 (처음엔 사람이 작성, 이후 👎 사례에서 추가).
2. **배포 전 회귀 테스트**: 프롬프트/모델 변경 시 골든셋 돌려서 점수 비교. Jest처럼 "품질 테스트"를 CI 느낌으로.
3. **Judge 캐시**: 같은 (질문, 답변) 쌍은 재채점 안 함 → 비용 절감.
4. **대시보드**: 주간 평균 점수 추이 1개 그래프면 충분. (MyHub 상단바 스타일로 간단히)

### 4.4 항목 평가

| 항목 | 내용 |
|------|------|
| **적용 난이도** | **하~중** (👍/👎 + 경량 지표는 하, LLM-as-judge 배치 + 골든셋은 중) |
| **예상 효과** | **중~대** — 당장은 안 보이지만, 프롬프트를 고칠 때마다 "좋아졌는지" 숫자로 아는 것과 모르는 것의 차이가 누적됨. "QA는 Jest 커버리지 숫자로"라는 사용자 원칙과도 일치 |
| **무료 원칙 충돌** | **없음** — 채점용 저비용 모델도 기존 무료 키로 충당. Judge 호출량은 답변 수의 일부(샘플링)로 조절 가능 |

**주의**: 평가는 "측정"이지 "목적"이 아님. 점수 올리기에 집착하면 비서가 시험 잘 보는 앵무새가 됨. 👎 사유와 함께 보는 게 핵심.

## 종합: 우선순위 제안

| 순위 | 주제 | 이유 |
|------|------|------|
| 1 | **Proactive (아침 브리핑 + Web Push)** | "진짜 비서" 체감 변화가 가장 큼. Cron 5개 무료, Web Push 무료. 기술 리스크도 낮음 |
| 2 | **장기 메모리 (FTS5 기반)** | 브리핑·리마인드가 "기억"과 결합될 때 시너지. Vectorize 없이 D1만으로 시작 가능 |
| 3 | **품질 측정 (👍/👎 + 경량 지표)** | 1·2를 만들기 전에 깔아두면 개선 속도가 달라짐. 구현은 가장 쉬움 |
| 4 | **음성 인터페이스** | 유용하지만 사용 빈도·체감 대비 우선순위 낮음. 브라우저 API라 나중에 붙이기 쉬움 |

**공통 전제**: 4개 주제 모두 무료 원칙과 충돌 없음. 추가 카드·과금 동의 없이 구현 가능.
